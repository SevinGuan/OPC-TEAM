# opc-team 命令与配置手册

配套 `OPC-架构规范.md` v2.15。规范定义「必须怎么做」，本手册定义「怎么落地」。

> **宿主无关**：本 Skill 不限定任何 Agent 产品。文中「宿主」指当前执行它的 Agent 运行环境；Skill 目录、MCP 配置、凭证注入方式均由该 Agent 自行约定，本手册不预设厂商名称或路径。

## 1. 设计前提：逻辑键 → URI

规范与岗位卡**从不写物理路径**，只写逻辑键：

| 逻辑键 | 含义 |
|---|---|
| `L2/{project}/{step_doc}` | 某个项目某个阶段的产出 |
| `L3/{role}` | 某职业的简历 |
| `L4/{domain}/{rule_id}` | 某条规则 |

`opc.config.json` 的 `role_bindings` 把逻辑键解析成 URI。默认 `local://`；绑定外部后端后变成 `<后端名>://`（如 `yunxiao://` / `feishu://`）。**换后端不改规范、不改岗位卡、不改 Bot 提示词** —— 这是跨电脑、跨 Agent 复用同一套流程的关键。

产出索引 `30_项目/_产出索引.md` 是唯一的结构化出处：一行 = 一个职业在一个项目的一个落地物，含 `物理地址 URI`。相似项目检索、溯源、外部引用一律查这张表。

## 2. 配置文件字段

| 字段 | 说明 |
|---|---|
| `vault_root` | Vault 根目录；`init` 时自动写入实际路径 |
| `default_backend` | 默认 `local` |
| `active_profile` | 当前行业 profile（如 `app` / `content`）；`init --profile` 或 `opc profile <name>` 切换 |
| `profiles.<name>.label` | profile 显示名（如「内容创作 / 自媒体」） |
| `profiles.<name>.step_docs` | 该行业的流程文档名（有序，决定 `new` 生成哪些文档） |
| `profiles.<name>.step_owner` | 每份文档的归属职业与阶段号 |
| `profiles.<name>.role_bindings` | 该 profile 的职业集合与产出键 → 地址模板（同下） |
| `profiles.<name>.knowledge_domains` | `20_知识资产/` 下创建的知识域子目录 |
| `profiles.<name>.tags_vocab` | 该行业的类型标签词表（由 `governance` 维护） |
| `backends.<name>.type` | `local` 或 `exec` |
| `backends.<name>.cli` | 外部系统可执行命令名（由用户填写） |
| `backends.<name>.push_cmd` | 推送命令模板，占位符 `{file} {project} {role} {key} {ref}` |
| `backends.<name>.url_prefix` | 生成可打开链接的前缀；为空则用 `<name>://<ref>` |
| `backends.<name>.credential_env` | 所需环境变量**名称列表**，不存值 |
| `internal_layers` | L1/L3/L4 固定本地，不建议改 |
| `index_path` | 产出索引路径 |
| `security.credentials_in_config` | 必须为 `false` |

配置用 JSON（而非 YAML）是为了**零第三方依赖**：任意安装 Python 3 的机器都能直接跑。

两点约定：

- `ref` 填**目标系统内的相对地址**（如 `{project}/4_产品定义`），不要带 `http(s)://` 或系统名前缀，否则生成的 URI 会重复前缀；若确需填完整 URL，`resolve` 会原样返回。
- 产出索引记录的是**当时实际落地的地址**。中途改绑定只影响之后的产出，历史行的 URI 保持不变（这正是溯源需要的）。

### 2.1 两种后端选择（暂时只提供两种）

| 选择 | 后端键 | 产出落在哪 | 适用 |
|---|---|---|---|
| **本地（默认）** | `local` | **架构规范 §2 定义的 Vault 目录内**，即 `30_项目/PXXX/...` 与 `99_Agent配置/...` | 不填任何外部配置即可用；双链、Git 回滚全部有效 |
| **外部 CLI 后端（exec）** | `exec`（内置示例：`feishu` / `yunxiao` / `dingtalk`） | 由 `push_cmd` 推送到外部系统，URI 由 `url_prefix` 或 `<name>://` 生成 | 需要把某职业产出同步到任意外部系统（云效 / 飞书 / 钉钉 / 自定义）。**都是可选项**，接新系统只改 `label` / `cli` / `push_cmd` / `credential_env`，**无需新代码** |

> **创始人后端分工决策（2026-11-13，仅记录不改机制）**：
> ① **代码与工程**（代码仓库 Codeup / CI/CD Flow / MR）→ **阿里云云效**（官方 `aliyun devops` CLI 或社区 `yunxiao-code`，凭证走环境变量 `ALIBABA_CLOUD_YUNXIAO_ACCESS_TOKEN`）；
> ② **协同与项目协作**（群通知、审批、工作项、项目看板）→ **钉钉**（与云效原生整合，同一组织内打通：云效的流水线 / 代码事件可推钉钉群，钉钉审批可驱动云效流程）；
> ③ **不涉代码的文档资产**（约束卡 / MRD / BRD / 产品定义套件 / 架构文档 / 复盘）→ **飞书**（文档与知识库生态）。
> 三者都走本手册 §2 的 `backends` + `bind` 机制（`exec` 后端，label / cli / push_cmd / credential_env 四项），无需新增后端类型。云效管代码、钉钉管协同、飞书管文档，三者职责分离、凭证均只存环境变量名，值不进 Vault。

> **数据资产双份机制（2026-11-13，仅记录）**：产品 / 设计 / 架构等所有数据资产**本地仓库必有一份**（Vault 内，Git 可回滚），远程仓库（云效 / 飞书）是**同步副本**——`opc bind` 把某职业产出绑到后端后，本地仍留原件、远程多一份可共享可审计的副本。**本地是唯一真相源**，远程同步失败不影响本地；版本以本地 Git 为准，远程仅作协同与留档。

**本地产出不会写到别处**：默认 `role_bindings` 的每条 `artifacts` 都指向规范 §2 里的相对路径。唯一例外是外部后端不可用时，降级暂存到 `00_收件箱/agent-output/`（索引标 `待同步`），仍在 Vault 内。

## 3. 命令速查

```bash
V=./OPC-Vault

python scripts/opc.py init                       # 不带路径 -> 交互式引导（选目录 + 选 profile）
python scripts/opc.py init --choose              # 尝试弹出系统目录选择框
python scripts/opc.py init --vault $V --profile content --non-interactive
python scripts/opc.py profile --vault $V         # 查看当前与可选 profile
python scripts/opc.py profile content --vault $V # 切换（既有索引行保留为历史记录）
python scripts/opc.py status --vault $V

# 第二种选择：绑定外部 CLI 后端（以下以云效为例；换 feishu / dingtalk / 自定义同理）
python scripts/opc.py bind-cli yunxiao \
  --cli "<目标系统 CLI 或 python>" \
  --push-cmd "<CLI> doc create --folder {ref} --file {file}" \
  --url-prefix "https://<域名>/repo" --vault $V
python scripts/opc.py bind pm yunxiao --key 4_产品定义 --ref "{project}/4_产品定义" --vault $V
python scripts/opc.py resolve pm 4_产品定义 --project P001 --vault $V

python scripts/opc.py new 会员工具 --tags "#订阅制 #高频工具 #B端结算" --vault $V
# 按需路由：分诊结论由 pm 写在 4_产品基线.md，--scope 只是把该结论落成命令参数
python scripts/opc.py new 页面微调 --scope 画面 --from P001 --vault $V
python scripts/opc.py new 接口迭代 --scope 后端 --from P001 --vault $V
python scripts/opc.py similar --tags "#订阅制 #B端结算" --vault $V
python scripts/opc.py similar --tags "#订阅制" --role engineer --vault $V

# 项目出处闭环：收尾回填 -> 按职业查全部经验 -> 按项目反查全部职业
python scripts/opc.py close P001 --link --vault $V
python scripts/opc.py resume pm --vault $V
python scripts/opc.py trace P001 --vault $V

# 版本链（v2.17）：创建项目 = V1；项目内追加一次立项 = 新版本号
python scripts/opc.py version list --project 会员工具 --vault $V
python scripts/opc.py version new --project 会员工具 --需求 "把积分改成跨门店通用" --vault $V

# 产出按需生成（v2.18）：立项只登记，岗位开工时只生成自己那一份
python scripts/opc.py scaffold --role pm --project 会员工具 --vault $V
python scripts/opc.py scaffold --role design --project 会员工具 --version V2 --vault $V

# 知识沉淀（v2.17）：派发清单 -> 各岗自己写自己的履历 -> 汇总
python scripts/opc.py distill --project 会员工具 --vault $V
python scripts/opc.py link --project 会员工具 --version V2 --role design --vault $V
python scripts/opc.py distill --status --project 会员工具 --vault $V

# 存量 Vault 迁移（v2.17）：目录名去 P00X 前缀 + 补 V1 台账
python scripts/opc.py migrate --dry-run --vault $V
python scripts/opc.py migrate --vault $V
```

`init` 幂等：已存在的文件一律不覆盖。`new` 自动分配 `PXXX` 编号、**只登记版本台账与索引行**（**不生成产出文件**，见 §42.2.1）、输出相似项目。`link` 只写**结构化骨架**（关联项目、产出地址、标签、证据指针、待补字段），「怎么落地的 / 坑与解法 / 结果」仍由各职业 Agent 补写。

> **v2.17 起**：`new` 建的项目目录叫 `项目名_YYYY-MM`（不再带 `P00X_` 前缀），`PXXX` 退为**内部短 ID**（索引末列 `ID`、状态文件名 `_交接状态/P001.json`）；`link` 的条目标题也变成 `### 项目名 · YYYY-MM · V<N>`（不带项目号）。详见 **§42 版本链与知识沉淀（v2.17）**。
>
> **v2.19 起**（ADR-0007）：项目目录名**去掉年月**（= `项目名`，同名加 `-2`），时间维度下沉到**版本目录** `YYYY-MM-DD-V<N>`（日期 = 该版本立项日）。

### 3.1 交互式初始化引导（回答「会不会弹框让我选目录」）

| 场景 | 行为 |
|---|---|
| Skill 由 Agent 加载 | **由 Agent 按 SKILL.md 的引导流程逐项询问**：保存目录 → 项目名与标签 → 本地/外部 CLI 二选一 →（若外部）CLI 与凭证变量名。这是对话式交互，跨电脑、跨 Agent 都稳定 |
| 脚本直接运行 `init` | 不带 `--vault` 时提示「Vault 要保存在哪里？」 |
| 脚本运行 `init --choose` | 尝试用 tkinter 弹出**系统目录选择框**；无图形界面 / 无 tkinter 时自动退化为文本输入 |
| 批量自动化 | 加 `--non-interactive` 关闭全部询问 |

**不会凭空猜测盘符或目录**：未指定且非交互环境下统一回退到 `./OPC-Vault`。`new` 不带项目名、`bind` 不带后端时也会进入对应的引导。

### 3.2 简历与项目出处的绑定（回答「三份经验都能找到出处吗」）

`link <PXXX>` 会为该项目涉及的每个职业做三件事，且**幂等**（已有 `### PXXX` 条目则跳过）：

1. 在职业简历 `## C 项目经历` 追加一条，含 `关联项目：PXXX → [[30_项目/_产出索引#PXXX]]`、`本职业产出地址`（本地路径或云端 URI）、类型标签、证据指针。
2. 更新 frontmatter 的 `project_refs: [P001, P002, P003]`。
3. 重建 `## D 相似经验速查` 表（按标签聚合项目）。

于是「产品经理简历有 3 份项目经验」可用 `resume pm` 一次列出：每份经验的标签、产出地址、对应索引行与简历条目；`trace P001` 则反向列出该项目下 8 个职业的落地物。简历 C 节只增不改，历史条目不会被覆盖。

## 4. 第二种选择：绑定外部 CLI 后端（云效 / 飞书 / 钉钉 / 任意自定义）

1. 按**目标系统**（云效 / 飞书 / 钉钉 / 其它）官方文档准备凭证与可用 CLI / webhook；哪个都不是必备，只用你实际需要的那个。
2. 把凭证**只放进环境变量**（示例变量名，值不要写进任何文件）：
   如 `ALIBABA_CLOUD_YUNXIAO_ACCESS_TOKEN`（云效）、`DINGTALK_WEBHOOK_URL`（钉钉）、`FEISHU_APP_ID`（飞书）——按你实际用的系统取，不必全配。
3. 执行 `bind-cli`，填入实际 CLI 名与 `push_cmd` 模板；模板中的 `{file}` 会被替换为本地产出路径，`{ref}` 为绑定地址。
4. 执行 `bind <role> <后端名> --key <产出键> --ref <地址模板>`（`<后端名>` 取 `feishu` / `yunxiao` / `dingtalk` / 你自定义的条目），把具体职业指向该外部系统。
5. 执行 `status` 确认环境变量已设置（只显示「已设置 / 未设置」，不显示值）。
6. 执行 `resolve <role> <key> --project P001` 验证得到可打开的 URI。

**本 Skill 不预设任何厂商的 CLI 名称、参数或 API 细节**，这些必须以对应系统官方文档为准。切到另一个外部系统时，复用 `exec` 后端类型，只把 `label` / `cli` / `push_cmd` / `credential_env` 改成对应系统即可，**无需新增后端类型、无需改代码**；`credential_env` 里只写环境变量名，不写值。

## 5. 跨设备 / 跨 Agent 迁移

需要携带三样东西：

1. 整个 `opc-team/` 目录（放到新环境当前 Agent 约定的 Skill 目录（保持 `<skills 根>/<包名>/SKILL.md` 结构）下，保持 `<skills 根>/opc-team/SKILL.md` 结构即可被识别）。
2. `opc.config.json`（含后端绑定）。
3. Vault 数据；若产出已在云端，则只需配置与索引，本地可只保留 L1/L3/L4。

到新机后执行 `status`。若外部后端不可用，产出降级到本地 `00_收件箱/agent-output/`，索引标 `待同步`，**不静默丢弃**。

创建新 Bot 时：把 `assets/岗位卡/<role>.md` 与 Vault 根目录的 `OPC-架构规范.md` 一起交给它；Bot 按规范 §0 报告 role / 阶段 / project / 输入文件，并按 §15.7 检索相似经历。

## 6. 限制与风险

| 限制 | 说明 |
|---|---|
| 双链不跨系统 | Obsidian `[[双链]]`、反链、Dataview 只在 Vault 内生效。产出上云后，溯源**只能**靠产出索引的 URI |
| 分层不建议全上云 | L1 骨架、L3 简历、L4 规则保持本地，保证双链、Git 版本控制与一键回滚；只有 L2 产出层适合外部化 |
| Git 不覆盖云端 | 外部系统的版本与权限自行管理；云端产出必须在索引登记 URL 与同步时间 |
| 简历不是执行依据 | 相似经历仅作参考，适用与否按规则层 `applies_when` / `counter_example` 判断，禁止照抄 |
| 凭证安全 | 禁止把 app secret / token 写进配置、简历或任何入库文档；`status` 只检查是否存在，不打印值 |
| 外部命令 | `push_cmd` 由用户填写并自行承担执行风险；未配置 CLI 或缺少环境变量时不执行、降级本地 |

## 7. 故障排查

| 现象 | 检查 |
|---|---|
| `未登记的 role / backend` | 配置的 `role_bindings` / `backends` 是否含该键 |
| `resolve` 返回 `解析失败` | `artifacts` 是否含该产出键；`{project}` 对应目录是否存在 |
| 外部后端报「未绑定 CLI」 | 执行 `bind-cli`；检查 `credential_env` 中的环境变量 |
| `similar` 无结果 | 索引行的「状态」是否仍为 `进行中`；标签是否与词表一致 |
| `close` 提示简历未追加 | 执行 `close <PXXX> --link` 或 `link <PXXX>` 回填出处；内容由对应职业 Agent 补写 |
| 想看某职业的全部项目经验 | `resume <role>`；按项目反查所有职业用 `trace <PXXX>` |
| `init` 停在询问、不想交互 | 加 `--non-interactive --vault <path>` |
| `--choose` 没弹出目录框 | 当前环境无 GUI 或无 tkinter；脚本已自动回退为文本输入，也可直接 `--vault <path>` |
| 换机后路径不对 | 执行 `init` 会重设 `vault_root`；或手工改配置中的 `vault_root` 与 `backends.local.root` |
| 宿主不支持创建多个 Bot | 用默认的 `agent_mode: single`，见 §8 |
| 想换行业但不想重建 Vault | `opc profile <name>` 切换即可；既有项目索引行保留为历史记录，新项目按新 profile 建（见 §9） |
| 新 profile 的职业没有岗位卡 | 重新执行 `init`（幂等）：缺卡职业自动生成九节骨架卡，首个项目开工前补全 |
| `未登记的 role` 但明明有这个职业 | 当前 `active_profile` 的职业集合里没有它；`opc profile` 查看，或切换 profile |

## 8. Bot 部署：Skill 不自动创建机器人

### 8.1 能力边界（重要）

本 Skill 是**岗位说明书 + 工作台**：提供规范、8 份岗位卡、8 份职业简历、产出索引与命令脚本。它**不能**在宿主产品里注册 Bot 实例、指定模型、授予工具权限或挂载知识库 —— 这些是宿主平台的能力，创建动作必须由用户完成。不同产品差异很大，且**并非都支持多个机器人**，因此 Skill 不把「多 Bot」当作前提。

**但这套流程不依赖多 Bot**：职责边界靠「本次加载哪份岗位卡 + `scope` 契约 + 写前自检」实现，而不是靠物理隔离的 Bot。不支持多机器人的产品一样能跑完 9 步。

### 8.2 运行模式（`agent_mode` 的四档）

| 模式 | `agent_mode` | 前提 | 做法 | 适用 |
|---|---|---|---|---|
| 单 Bot 切换（**默认、推荐**） | `single` | 任何支持自定义提示词 / 知识库的 Agent | 只用一个 Bot；每次开工 `opc role <role>` 取得身份声明，本次会话只按该岗位卡执行 | 绝大多数产品；一人公司最实用 |
| 多 Bot 并行 | `multi` | 宿主支持创建多个 Bot | `opc bots` 导出 8 份配置卡 → 手动建 8 个 Bot，各贴一份 | 平台支持且确实需要并行时 |
| 多 Profile 增强 | `multi-profile` | 宿主支持**独立持久身份 + 独立记忆**（Profile 型宿主） | `opc bots` 导出卡 → 每份卡第五节给出 SOUL.md / 共享 workspace / 记忆归属，逐个 Profile 照做 | 要真正的身份隔离与持久记忆 |
| 脚本编排 | （任意） | 宿主提供 API / CLI | 外部脚本按 9 步依次调用同一 Agent，每次注入不同岗位卡 | 自动化流水线 |

> **三档「多 Agent」是三种互不兼容的形态，不是同一件事的大小分档**（工作区根 `GLOSSARY.md` 第五节 / `docs/adr/0001-多agent协同形态.md`）：
> **对话式团队**（主 Agent 调度子 Agent、互相 @ 唤醒）—— OPC **不采用**，宪法 §15.3 禁止 Agent 间对话内传递；
> **独立身份**（一职业 = 一个独立 Agent 实例）—— `multi` / `multi-profile` 提供的就是它；
> **文件式流水线**（pull 式认领）—— OPC 的协同形态。
> ⚠️ **独立身份 ≠ 流水线并行**：8 个 Agent 存在 ≠ 8 条流水线并行，并行度取决于**波次数量**（不同项目），见 §22.2 / §23.4。

**单 Bot 模式仍满足规范 §15.1「一 Agent 一岗位」**：物理 Bot 可复用，但每次会话只绑定一个 `role`、只加载一份岗位卡、只按该 role 的 scope 写入。换角色必须开新会话重新声明，禁止一次会话兼任两个职业。

### 8.3 单 Bot 模式操作

```bash
python scripts/opc.py role pm --vault $V
```

把输出的「本次身份声明」粘贴到当前 Bot 的对话开头或系统提示词；它会带上：只负责 / 明确不负责的阶段、必读文件清单、本岗主产出 URI、越界拒绝规则。做完这一阶段后开新会话，换 `role engineer` 继续。

### 8.4 多 Bot 模式操作

```bash
python scripts/opc.py bots --vault $V          # 导出到 $V/99_Agent配置/Bot配置卡/
python scripts/opc.py bots --out ./bot-cards --vault $V
```

每份 `Bot配置卡_<role>.md` 含五部分：可直接粘贴的系统提示词、需要挂载的文件清单、主产出地址、**岗位卡全文附录**（避免两处维护）、**Profile 宿主适配段**（v2.13 新增）。用户只需在宿主里逐个创建实例、复制提示词、挂载文件。

宿主侧需要用户自行决定的项（Skill 不代填、不臆造任何平台的具体能力）：模型、上下文长度、工具/文件访问权限、知识库或文件挂载方式、是否允许联网、Bot 数量上限。

### 8.5 运行模式怎么改（`opc mode`）

```bash
python scripts/opc.py mode                 # 查看当前模式与各档说明
python scripts/opc.py mode multi           # 切到多 Bot
python scripts/opc.py mode multi-profile   # 切到多 Profile 增强
```

`opc mode` 是 `agent_mode` 的**唯一写入入口**（v2.13 起）。此前该字段只被读、从未被写，用户只能手改 `opc.config.json`；现在 init 引导也会问这一项（团队形态是安装握手的一部分）。

- 写入收敛到脚本内单一函数 `set_agent_mode()`，取值 `single` / `multi` / `multi-profile`，其它值直接报错。
- **幂等**：已是目标值时不重复写；`init` 重跑也不覆盖已定下的模式。
- 切到 `multi-profile` 后跑 `opc onboard`，会按该模式输出 Profile 专属引导（含「workspace 必须指向同一个 Vault」的硬前提）。

### 8.6 常见误解

| 误解 | 事实 |
|---|---|
| 「装了 Skill 就自动多出 8 个 Bot」 | 不会。Skill 只产出配置卡与岗位定义 |
| 「职业定义要自己一个个写」 | 不需要。8 份岗位卡与配置卡已生成，只需复制粘贴 |
| 「宿主不支持多 Bot 就没法用」 | 可以用 `single` 模式，一个 Bot 按阶段切换身份 |
| 「单 Bot 会串岗」 | 边界由岗位卡 + scope + §14 自检约束，不靠物理隔离 |
| 「换行业要重做整个 OPC 架构」 | 不需要。骨架行业无关，只换 profile（见 §9） |

## 9. 行业 profile：换行业不换架构

### 9.1 什么变、什么不变

| 层 | 换行业时 | 内容 |
|---|---|---|
| **骨架（不变）** | 零改动 | 四层架构 L1–L4、一文件一 owner、scope 边界、简历自进化（link/resume/trace）、逻辑键→URI、产出索引、全部命令、后端类型只有 `local` / `exec` 两种（`exec` 下可配任意外部系统） |
| **皮肤（随 profile 换）** | 只换配置段 | 流程文档名（`step_docs`）、每步归属职业（`step_owner`）、职业集合（`role_bindings`，可增减职业）、知识域（`knowledge_domains`）、标签词表（`tags_vocab`） |

任何交付型生意都存在「洞察 → 立项 → 定义 → 产出 → 验证 → 交付 → 迭代」的同构阶段；profile 只是给这套骨架换一套行业化的名字与分工。

### 9.2 内置 profile 对照

| | `app`（默认） | `content` |
|---|---|---|
| 定位 | APP / 互联网产品 | 内容创作 / 自媒体 |
| 流程 | 约束卡 → MRD → 立项 → BRD → PRD → 设计与方案 → 实现与测试 → 上线 → 复盘 | 约束卡 → 选题洞察 → 立项 → 内容定位 → 内容策划案 → 文案与视觉 → 审校与合规 → 发布与分发 → 复盘 |
| 职业集合 | strategist / market / pm / design / **engineer** / growth / governance | strategist / market / pm / design / **editor** / growth / governance |
| 知识域 | 行业洞察、商业模式、产品方法、设计规范、技术架构、增长与运营、合规与财务 | 行业洞察、商业模式、内容方法、增长与运营、合规与财务 |
| 岗位卡 | 8 份手写完整版（Skill assets 内置） | 6 份复用 assets + editor 骨架卡（`init` 自动生成） |

### 9.3 怎么用

```bash
# 新 Vault 直接选行业
python scripts/opc.py init --vault $V --profile content

# 已有 Vault 切换行业（既有项目索引行保留为历史记录）
python scripts/opc.py profile content --vault $V
python scripts/opc.py init --vault $V --profile content   # 幂等补建新 profile 的目录与骨架卡
```

### 9.4 新增行业（如咨询、电商、教育）

在 `opc.config.json` 的 `profiles` 里加一段即可，**脚本零改动**：

1. 复制一份最接近的 profile 段，改名（如 `consulting`）与 `label`。
2. 按该行业改写 `step_docs`（保持 0–8 的阶段编号与「洞察→…→复盘」同构）、`step_owner`、`role_bindings`（职业可增减，如去掉 engineer 加 delivery）、`knowledge_domains`、`tags_vocab`。
3. 执行 `init --profile consulting`：缺卡职业自动生成九节骨架卡（含自动填好的阶段、权限、红线），由创始人 + Agent 在首个项目开工前补全带「待补」的条目；可参照 `app` profile 的同名岗位卡。
4. 岗位卡的九节结构、简历五节结构、规范宪法不随行业变。

**经验跨行业沉淀**：所有 profile 共用同一个 Vault、同一张产出索引与同一批简历。内容公司的 pm 做过「知识付费」项目后，app 公司的 pm 在 `similar` 检索时同样能看到这份经验（是否适用按规则层 `applies_when` 判断）。

## 10. 交接通知与人工步进（§15.9）

项目由 `new` 写入 `active_project`，之后**不用再传项目号、不用记命令**。

| 场景 | 谁执行 | 效果 |
|---|---|---|
| 本岗产出完成（含任意格式附件） | Agent | `opc done --role market --file 图片.png` → 校验落盘 → 通知创始人 → 挂起 |
| 创始人回「继续 / 下一步 / 通过 / 驳回」 | 当前会话代为执行 `opc go` | 校验回执 → 输出紧邻下一棒的身份声明 → 游标 +1 |
| 创始人回「不同意 / 驳回 / 要改」 | 当前会话代为执行 `opc go --decision 驳回` | **退回本阶段、游标不推进**，当前 role 补充后重报 |
| 想看当前停在哪 | `opc handoff` | 显示项目、阶段、状态、回执、下一棒、通知通道 |

**「当前会话」就是创始人正在说话的那个会话**（§15.9：*在会话里回「继续 / 通过」，当前会话代为 `opc go`*）。多 Bot 场景下，这意味着：创始人**在群里 @ 那个角色**回「继续」，**该角色的会话**就地执行 `opc go` —— 不需要切到 pm 会话、也不需要 @ 别的机器人。下一棒角色由 `go` 派活通知主动**在群里 @ 创始人**（v2.27 群内唤醒；`mode=dm` 时退回私聊）。

> v2.27 起群内唤醒：**唤醒由角色 @ 创始人**（飞书红点提醒，创始人零操作），
> **交互由创始人 @ 该角色**（`require_mention=true` → 只有被 @ 的那个角色醒，其余不受打扰）。
> 派活 / 汇报通知都带**项目号**（`PXXX` + 项目名），多项目并行时靠 `--project` 精确定位，
> 不会推进错项目。

- **驳回 / 需补充：闸门与非闸门都适用（v2.25）**。v2.23 曾把 `--decision` 限死为「只对人工闸门有效」——那针对的是**「通过」**错位（实测把 P003 阶段 2 的闸门结论记到了 P002 阶段 5 上）。但「驳回 / 需补充」在非闸门棒上语义完全成立（不满意 → 退回重做）。过去非闸门棒没有这条通道 → 创始人只能说「不行」，状态却卡在「待确认」，而 `opc done` 又拒收重复提交 → **流程死锁**。v2.25 规则：非闸门棒**只接受** `驳回` / `需补充`，`通过` 仍然拒绝（等价于不带 `--decision` 直接推进）。
- **派活私聊（v2.24）**：`notify.dispatch` 段开启后，`opc go` / `opc advance` 推进成功会用**下一棒角色自己的飞书应用身份**私聊创始人告知「轮到你开工」；`opc done` 后用**本角色自己的身份**私聊汇报完成。创始人**全程不需要 @ 任何职业机器人**。收件人用 `union_id`（跨应用统一；`open_id` 按应用隔离，跨 bot 发私聊会报 `99991 open_id cross app`），走环境变量 `FEISHU_FOUNDER_UNION_ID`；凭证只从各角色 profile 的 `.env` 读，**不入库**。发送失败**不阻塞流程**（§15.12），降级为群内通知。

- **群内唤醒的 allowlist（v2.28 · 实测最易踩的坑）**：每个职业 profile 的 `.env` 里另需 `FEISHU_ALLOWED_USERS`，填**该角色自己应用视角下的创始人 open_id**（`ou_` 开头）。三种 ID 各管一段，**填错就是「群里 @ 角色永远不吭声」且界面上没有任何报错**：
  | ID | 形态 | 作用域 | 用在哪 |
  |---|---|---|---|
  | `open_id` | `ou_...` | **按应用隔离**（同一人在 5 个职业应用下有 5 个不同值） | `FEISHU_ALLOWED_USERS`（谁能跟这个 bot 说话） |
  | `union_id` | `on_...` | **跨应用统一**（全租户同一个值） | `FEISHU_FOUNDER_UNION_ID`（派活私聊发给谁） |
  | `user_id` | `u-...` / 数字 | 租户内 | 少用 |

  **不能用 union_id 代替 open_id**：allowlist 匹配的是「该应用看到的你」，填 union_id 一律不匹配。取法：①Hermes 向导里选「Only allow listed user IDs」会自动填对（推荐）；②建应用时扫码那位就是创始人，其 open_id 在扫码产物里；③实在拿不到，从网关日志里抄——`journalctl --user -u hermes-gateway | grep "Unauthorized user"` 打出的 `ou_xxx` **就是**该应用视角下你的 open_id（哪个角色报的就填哪个角色）。
  症状与对策：群里 @ 某角色无反应 + 日志有 `Unauthorized user: ou_xxx ... on feishu` → 把该 `ou_xxx` 写进那个角色的 `FEISHU_ALLOWED_USERS`，改完重启网关生效。`opc init` 收尾的「多 Bot 群内唤醒自检」会逐角色核对这一项（填成 union_id 会被点名）。

- **通知通道**：`notify.channel = local` 时追加到 `99_Agent配置/_交接通知.md`。**外部通道都是可选的，且不影响流程推进**：通知只是「可以进下一步」的提示，`opc done` 无论通道是否配置/是否成功都照常写状态并挂起，推进由创始人在会话里回「继续 / 通过」触发 `opc go`。内置三条示例：`feishu` / `dingtalk` / `yunxiao`（均为 `type: exec`）。`init` 会复制通用桥 `notify_webhook.py`（支持钉钉 / 云效 / Slack / 任意 HTTP webhook）与飞书专用桥 `notify_feishu.py`。启用任一条只需两步：设置对应 webhook 环境变量（`FEISHU_WEBHOOK_URL` / `DINGTALK_WEBHOOK_URL` / `YUNXIAO_WEBHOOK_URL`，或通用 `OPC_WEBHOOK_URL`），把 `notify.channel` 改成该名称。`push_cmd` 占位符含 `{file} {project} {role} {key} {ref} {vault}`，`{file}` 是通知文本。接其它系统再加一个 exec 条目即可，无需写代码。外部通道未配或失败自动降级 `local`，通知不丢。**凭证值不写配置文件**。
- **防跨步**：`done` 没有目标角色参数，下一棒只能由 `step_docs` 顺序推导；完成状态以主产出文件 + frontmatter 为准，Agent 自称不算；状态与一次性回执在 `99_Agent配置/_交接状态.json`。阶段 0 / 2 / 7 是闸门，`go` 必须带 `--decision 通过|驳回|需补充`，可选 `--basis <依据>`；**拍板一律留痕**——`decision` / `decided_by` / `decided_at` / `decision_basis`，**「通过」同样记录**（v2.11；此前只有「驳回 / 需补充」记录，「通过」连字都不留）。
- 通知只发给创始人，Agent **禁止**自行 @ 或唤醒下游（§15.3）。协作角色（阶段 5/7/8 的 H2 章节）不推进游标，由 owner 汇总报完成。

## 11. 资产快照（§15.10）

`opc done` 自动生成 `30_项目/PXXX/_资产快照.md`，一次交接一个批次，含项目 / 阶段 / 职业 / 时间 / 上游 / commit，以及每份资产的路径、格式、版本、时间、大小、SHA256。

```bash
python scripts/opc.py assets --role market --vault $V   # 按职业查视图
```

- 唯一台账就是这份文件；职业视图由命令查询生成，**不另建 8 份台账**（§1 原则 4）。
- 资产版本独立自增（md 取 frontmatter 的 `version`，其余按出现次数 `v1.N`），**不要求代码跟着迭代**；快照记 commit，`done` 会输出带批次号的建议提交信息，形成双向指针。
- 图片 / 附件 / 表格只登记指纹与路径，实体留 Vault 或外部后端，不进 Git 索引。

## 12. 长连接收确认（可选，§15.9）

发通知与收确认是两件事：`notify.channel` 负责**发**，`notify.confirm_listener` 负责**收**你在该通道回的「继续 / 通过 / 驳回 / 需补充」（当前实现基于飞书长连接，属可选组件；未启用时在当前会话直接回话即可）。

## 13. 工具治理（§15.11）

### 13.1 注册表可写吗

**可写，但只有创始人能写，Agent 只读。** 全局 `99_Agent配置/工具注册表.md` 是唯一真相源；新增或变更必须：

```bash
python scripts/opc.py tools promote --id tool:xxx --approve --vault $V
```

没有 `--approve` 时脚本直接拒绝。Agent 不能把项目里用过的工具自己写进注册表，也不能改岗位卡或总规范。

### 13.2 项目里用了非预置工具

```bash
python scripts/opc.py tools add --role market --id tool:xxx --name "某竞品情报 MCP" \
  --type mcp --slot 竞品情报 --env SOME_API_KEY --vault $V
python scripts/opc.py tools --role market --vault $V
python scripts/opc.py tools propose --id tool:xxx --reason "两次调研都靠它" --vault $V
```

- `add` 只写 `30_项目/PXXX/_工具配置.md`（每项目一份、只增不改、随项目归档），**注册表不变**，仅本项目生效。
- `propose` 在 `00_收件箱/agent-output/tools/` 生成提议，等创始人 `promote --approve`。
- `promote` 写入注册表时默认 `status: 候选`、`preset: false`；要成为新项目默认预置，还需 ≥2 项目印证 + §9 四判据 + 版本 +0.1。

### 13.3 API Key 与 MCP

- `--env` 只登记**环境变量名**（如 `SOME_API_KEY`），值放宿主环境变量 / 密钥管理 / 已 gitignore 的 `.env`；Vault、注册表、简历、产出里都不写明文（`security.credentials_in_config: false`）。
- MCP server 的 `command` / `args` 属于**宿主配置**，不进 Vault；注册表只记「本工具依赖哪个 MCP、需要哪些环境变量名」。

`opc new` 把 `registry_version` 快照进项目层并写入 `0_约束卡.md` 的 `toolset_snapshot` / `pinned_refs`；全局注册表升级不影响在跑项目，解钉须先做 §11 变更影响评估。新项目重新初始化当前预置，项目结束随 `PXXX/` 进 `50_归档/`。

## 18. 怎么让 Agent 真正加载规范（防失控）

### 18.1 为什么光有 `OPC-架构规范.md` 不够

`CLAUDE.md` / `AGENTS.md` / `.cursorrules` / `GEMINI.md` 之类是**宿主自动加载的约定入口名**（各产品不同，以其官方文档为准）。我们的文件叫 `OPC-架构规范.md`，**不会被自动加载**。规范头部写「优先级高于 Agent 自身判断与历史对话记忆」只是**文本声明**，宿主是否照做取决于提示词有没有注入——文件躺在那里不等于规则生效。

### 18.2 三层叠加，缺一不可

| 层 | 做法 | 可靠性 |
|---|---|---|
| ① 系统提示词注入 | 建 Bot 时把规范 §0 的「下发包」直接粘进 system prompt；每次开工 `opc role <role>` 取身份声明贴进对话开头 | **最高**，不依赖宿主 |
| ② 入口文件 | 根目录 `AGENTS.md`（`opc init` 自动复制）只放**指针**：读规范全文 + 岗位卡 + 对应工作模式节 + §0 启动顺序 + 硬约束摘要 | 取决于宿主是否自动加载该文件名；用别的宿主就复制成 `CLAUDE.md` 等 |
| ③ 运行时校验 | `opc ask --role <role> --project <PXXX> --text "<要问什么>"` | **本岗主动问创始人 / 要拍板**（交互点专用）：用**本岗自己的**应用身份在群里 @ 创始人（红点提醒），**不推进游标、不产生资产批次**；交互内容落 `99_Agent配置/_交互留痕.md` |
| `opc done` 校验落盘与 frontmatter、§14 自检清单、闸门 0/2/7 人工拍板、Git 每次写入单独提交可回滚、资产快照 SHA256 | 事后可追溯，不能替代前两层 |

入口文件**不复制规范内容**（§1 原则 4 单一真相源），改规则只改一处。

### 18.3 失控风险与硬边界

常见失控来源：规则没加载 / 加载不全 / 被对话里的临时指令覆盖 / Agent 有写权限而自行改规则。前三个靠 ①② 解决；**第四个靠权限，不靠文字**——若宿主支持文件权限或工具白名单，把 `OPC-架构规范.md`、岗位卡 §1/§2/§6、工具注册表设为只读（§8 scope 是逻辑约束，宿主权限才是物理约束）。

### 18.4 文档长度的克制

宪法（`OPC-架构规范.md`）只放**不可变骨架、裁决规则与路由**；操作细节在岗位卡 §11/§12、工具在注册表、命令用法在本手册。新增机制时优先下放，**不再往宪法堆流程正文**。宪法短且稳，Agent 每次启动读全文才不吃上下文、才抓得住重点。

## 19. 两种接入场景：全新项目 vs 已有项目

Skill 的正确定位是**安装器 / 引导器**：它负责检测场景、决定 Vault 落点、复制文件、合并入口、输出报告；**运行时不参与每次对话**，Agent 读的是入口 → 规范 → 岗位卡。

### 19.1 全新空项目

```bash
python scripts/opc.py init --vault ./OPC-Vault
```

`init` 会建 Vault 骨架，并在**工作区根**（不是 Vault 子目录）创建一个 `AGENTS.md` 受控区块，指针自动带上 `OPC-Vault/` 相对路径。宿主若用别的入口名，复制该区块过去即可。

### 19.2 已有项目（已有 AGENTS.md / CLAUDE.md / 代码）

**不替换、不覆盖、不重建目录。** `init` 检测到已有入口时不会动任何文件，只提示执行：

```bash
python scripts/opc.py attach --vault ./OPC-Vault            # 只读诊断，列出会改什么
python scripts/opc.py attach --vault ./OPC-Vault --apply     # 受控合并
python scripts/opc.py attach --vault ./OPC-Vault --remove    # 卸载区块
```

- 默认检测 `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / `.cursorrules` / `.github/copilot-instructions.md`；可用 `--entry` 指定，或用 `--workspace-root` 指定宿主加载入口的目录。
- 合并方式：只在已有文件**末尾追加**一个 `<!-- BEGIN OPC-VAULT -->` … `<!-- END OPC-VAULT -->` 区块，**原有内容一行不动**；已有区块则幂等更新。项目原有代码、文档、Agent 配置一律不碰。
- OPC 自己的文件都待在独立的 `OPC-Vault/` 子目录（`vault_root` 可配），与项目原有目录不撞名。
- 一个项目都没有入口文件时，`--apply` 只新建 `AGENTS.md` 一个，不塞一堆配置文件。

### 19.3 为什么需要这一步

宿主自动加载的是**工作区根**的约定入口名，而 OPC 规范在 Vault 子目录里、文件名也不叫约定名 → 不合并就**不会被加载**。「优先级高于 Agent 判断」只是文本声明，入口没接上等于规则不生效。合并区块是**指针**，不复制规范全文（§1 原则 4），改规则只改一处。

三层加载仍是：① 系统提示词注入 §0 下发包（最可靠）② 入口文件受控区块 ③ 运行时自检与闸门。已有项目尤其别只靠 ②，建议把下发包也贴进 Bot 的系统提示词。

## 20. 安装期引导与「每个 Agent 该读什么」

### 20.1 不设「协调者 Agent」

协调职责拆成两段，**都不需要第 9 个 Bot**：

| | 归谁 | 机制 |
|---|---|---|
| 安装期协调（检测、初始化、引导逐个创建 Bot） | **Skill 本身** | `opc onboard`（只读诊断 + 下一步清单）；宿主不支持自动建 Bot，由用户按导出的配置卡手动创建 |
| 运行期协调（谁干完轮到谁） | 交接链 + 脚本状态机 + **创始人闸门** | §15.3 固定文件交接、`opc done` / `opc go`、§15.9 通知、闸门 0/2/7 人工拍板 |

§15.3 **禁止** Agent 间对话内传递，所以让一个 Bot 去 @ 另一个 Bot 是违规设计；且新增 Bot 会增加用户手动创建负担、违反 §1 原则 6「一 Agent 一岗位」。

### 20.2 一条命令看全貌

```bash
opc onboard --vault ./OPC-Vault
```

只读、幂等：Vault 骨架 → 宿主入口区块 → 岗位卡 → Bot 配置卡 → 当前项目状态，逐项标「已初始化 / 待办」并给出下一条命令；再列出 8 个职业的 Bot 创建引导。**已有工作流的项目**：检测到已初始化 / 已接入就显示「已完成」并跳过，不会重复初始化；缺入口时提示 `opc attach --apply` 受控合并。

### 20.3 每个 Bot 到底读什么（上下文分层）

| 层 | 内容 | 是否常驻上下文 |
|---|---|---|
| ① 启动顺序 / 硬约束摘要 | 入口区块 + `opc role <role>` 身份声明 | 是（几十行） |
| ② 自己的岗位卡 | 身份、阶段、权限、越界红线、验收、§11/§12 工作模式 | 是（本岗唯一职责定义） |
| ③ 自己的职业简历 | 只作相似经历参考与溯源，**禁止**当执行依据；禁止读别人的 | 按需 |
| ④ 当前项目交接文件 | 本岗 §8 权限内的上游交接文件（约束卡钉扎字段已逐级透传其中，宪法 §15.3） | 按需 |
| ⑤ 宪法全文 | 约束的**唯一真相源**，需裁决时按章节号回查 | **否**（不必全文常驻） |

要点：**Bot 受整份宪法约束，但不等于要把整份宪法塞进上下文**。`opc bots` 导出的系统提示词是宪法按 role 的**要点投影**（§1 六原则、本岗 §8 scope、闸门、§14 自检、红线）；需要裁决再按章节号回查全文。这样宪法保持唯一真相源，Bot 上下文却只有几百字。

> 宪法 §0 目前字面上仍要求「读全文」。要彻底改成上表的分层读取，属于 L1 变更，需创始人确认后在后续版本单独处理；在此之前用投影 + 按需回查的方式落地，不改宪法。

| 支持创建多个 Bot / 独立 Agent 定义 | `multi` | `opc bots` 导出 8 份配置卡，逐个在宿主创建；每职业一个 Bot |
| 支持独立持久身份 + 独立记忆（Profile 型宿主） | `multi-profile` | 一职业 = 一 Profile，岗位卡可作 `SOUL.md`，职业简历对应各 Profile 的独立记忆；Kanban 可当任务看板。`opc bots` 导出卡的第五节给出逐条适配指引 |

**关键**：规范 §8.1 已写明「这套流程不依赖多 Bot」——职责边界靠「本次加载哪份岗位卡 + scope 契约 + 写前自检」，不靠物理隔离。所以「只有少数宿主支持单独定义 Agent」并不阻碍落地；那是可选增强，不是前提。`opc onboard` 会按 `agent_mode` 输出对应引导（`single` / `multi` / `multi-profile` 三套）。

### Profile 型宿主的三个适配点

1. **共享 Vault 是硬前提**：Profile 的 `workspace/` 完全隔离，而 §15.3 的交接链依赖同一份 `30_项目/PXXX/` 与 `99_Agent配置/`。必须让所有 Profile 的 workspace 指向同一个 Vault（挂载 / 软链 / 共享路径），否则文件交接断掉。
2. **别造第二份真相**：宿主自带的 `MEMORY.md` / 长期记忆是它自己的；职业简历仍以 Vault 里 `99_Agent配置/履历/<role>.md` 为准（§15.6），避免两处记忆漂移（§1 原则 4）。
3. **看板 ≠ 闸门**：Kanban 可做任务分派与状态可视化，但阶段 0 / 2 / 7 的拍板仍归创始人；交接完成判定仍以文件落盘 + `opc done` 回执为准（§15.9），不要让主 Agent 的调度代替闸门。

> `opc bots` 导出的每份配置卡**第五节「Profile 宿主适配」**就是这三条 + 两条纪律（领活靠 pull 不靠 @ 唤醒）的可执行版，照做即可。

> ⚠️ 注：**「多智能体团队模式」（主 Agent 调度子 Agent、互相 @ 唤醒）与 §15.3 冲突** —— OPC 明确**不采用对话式团队**（工作区根 `GLOSSARY.md` 第五节 / `docs/adr/0001-多agent协同形态.md`）。宿主有这类能力时，可以拿它编排**同一波次内**的辅助工作，但**跨职业交接仍只走文件**，交接完成判定只认文件落盘 + `opc done` 回执。

## 22. 串行瀑布 vs 流水线（多波次并行）

### 22.1 现状说准

- `multi` 模式**支持** 8 个职业各一个独立 Bot / 独立 Profile（§21），但「有多个 Bot」≠「流水线并行」。
- 交接状态已改为**每项目一份**（v2.11+，§23.4）：`99_Agent配置/_交接状态/PXXX.json` 各自记 `step / token / status`；`active_project` 只是省略 `--project` 时的默认值，**不再是并行限制**。`opc go` 仍只允许 `i → i+1`，且须 `待确认` + 一次性 token。
- 因此现状是：**同一项目内**必须等上一阶段落盘 + 闸门通过；**不同项目可真正并行**（两个会话各写各的状态文件，互不覆盖；闸门 0/2/7 也按项目独立拍板）。
- 但**自动推进仍缺一环**：每步仍需 `opc done` 通知 + 创始人回「继续」→ `opc go`（§15.9），且没有外部编排器读文件状态自动推进（§22.4）。人工**调度**与人工**决策闸门**是两件事，前者可自动化，后者（0/2/7）按规范保留。

### 22.2 要的「流水线」是什么

一个需求波次 = 一个 project（`P001` / `P002`…），用 `30_项目/_项目关系.md` 的 `derived_from` 关联到上一波（§11，现成机制，不用改 §2 目录结构）。每个波次有自己的 9 步文档、自己的 `pinned_refs` 与游标；不同波次互不阻塞：

| 波次 | strategist | market | strategist | pm | … |
|---|---|---|---|---|---|
| P001 | 完成 | 完成 | 完成 | **进行中** | |
| P002 | 完成 | **进行中** | 等待 | | |
| P003 | **进行中** | 等待 | | | |

`pm` 在 P001 干活时，`market` 可以同时干 P002，`strategist` 干 P003——空闲的 Bot 接新波次的活，不用等整条链走完。§15.5「同一文件同一时刻只允许一个 Agent 写」天然满足：不同波次是不同文件。

### 22.3 只读第一步：`opc queue`

```bash
opc queue --vault $V                 # 所有项目当前阶段 / 接手 role / 状态
opc queue --role market --vault $V  # 只看 market 现在能领哪些活
```

依据各项目 9 步文档的 frontmatter `status` 推断，标出「可开工 / 待人工闸门 / 已走完」。这是**只读推断**，不改状态模型。**「待人工闸门」以交接状态里的 `gate` 标记为准**（v2.11 修正：此前按「下一个阶段号 ∈ gates」现算，与 `opc done` 的「刚完成的阶段」口径差一格，会把该拍板的漏报、把不该拍板的误报）。

### 22.4 要真正自动化还差什么（需创始人确认）

**v2.13 逐条核对**（与实现对齐，标掉已落地项）：

| # | 事项 | 状态 |
|---|---|---|
| 1 | `_交接状态.json` 从单游标改为**按 project 的任务卡集合** | ✅ **已实现**（v2.11+）：`99_Agent配置/_交接状态/PXXX.json` 每项目一份，§22.1 / §23.4 口径已同步 |
| 2 | `opc queue --role <role> --claim` 领任务：只领「同波次上游已完成 + 闸门通过」且 owner 匹配的任务；不同波次并行 | ✅ **已实现**（§23.1–§23.3） |
| 3 | 外部编排器读文件状态推进（§8.2 已预留「脚本编排」模式） | ✅ **已实现**（v2.14）：`scripts/orchestrator.py` —— 非闸门阶段自动推进一棒；闸门阶段**只推「待拍板」并停下**（拍板权仍在创始人）；**不**让 Bot 互相 @ 唤醒（§15.3），交接只走文件 + 通知通道。详见 **§40** |
| 4 | `agent_mode` 默认值与写入入口 | ✅ **已实现**（v2.13）：`opc mode <值>` + init 引导新增一问；`multi-profile` 档已补上（此前只有 `multi`） |
| 5 | 闸门 0 / 2 / 7 按波次人工拍板 | **保留不变**：不因并行而取消 |

## 23. 职业状态仓库：以「人」为中心的任务池

### 23.1 模型

**职业不依赖项目**：职业是「人」，项目只是他手上的活。人干完 A 项目的活、交接给下一棒之后不会闲着，而是去状态仓库看「我还有哪些项目的活没干」，继续领。这是现实企业 / 大厂任务看板的标准模型（Jira 的 My Issues、Kanban 的 assignee 视图）。

- **同一项目内串行**（§15.3 交接链、`opc go` 单步游标、闸门）——保留。
- **不同项目并行**：P001 在阶段 4、`pm` 忙；P002 在阶段 1、`market` 忙；P003 在阶段 0、`strategist` 忙，互不等。
- **pull 模式**：空闲的 Bot 自己去池子查活，**不由其他 Agent 唤醒**（§15.3 禁止对话内传递）；通知里可附「你的队列还有 N 条」作为提示。

### 23.2 状态仓库落点

| | 离线（本地仓库） | 在线（外部台账后端：飞书 / 未来的 Gitee 等） |
|---|---|---|
| 任务状态真相源 | **各项目 9 步文档的 frontmatter `status`（唯一权威）** | 台账镜像行 —— **副本与入口，不作真相源**（§15.8） |
| 职业认领 | `99_Agent配置/_职业任务池.json`（`claims` + `history`） | 台账「任务执行人 / 认领时间」列（副本；本地 `claims` 为准） |
| 当前会话游标 | `99_Agent配置/_交接状态.json` | 台账「进展 / 闸门 / 拍板结论」列（副本；本地状态为准） |
| 完成通知 | `99_Agent配置/_交接通知.md` 或 `notify.channels.<通道名>` | 外部通道消息 / 长连接收确认（§15.9，均为可选） |

外部表建议字段：`project / stage / doc / owner_role / status(可开工·进行中·待确认·完成·阻塞) / gate / token / 认领人 / 认领时间 / 上游 / 证据链接`。Bot 空闲时查「`owner_role=我` 且 `status=可开工`」即可。**默认仍是本地仓库**；外部后端走 `backends` + `bind`（`exec` 类型）与 `notify.channels`，按目标系统官方文档准备凭证与表格 schema，本 Skill 不预置厂商细节。

> **v2.15 已落地的一套实例（飞书多维表格台账）**：五张业务表与 OPC 五层一一对应，逐字段口径见 **宪法 §15.17.3**；表结构的真相源在仓库 `scripts/base_schema.py`，改表 = 改文件 + 跑一次 `--apply`，**不在飞书界面手点**。台账**是副本与入口，不是真相源**（§15.8）：本地 `_职业任务池.json` / `_交接状态.json` 才是「谁领了活、棒走到哪」的权威，云端那份只用于**看**与**派活**。详见 §41。

### 23.3 命令

```bash
opc roster --vault $V                          # 8 个职业各自状态 + 可领任务数
opc queue --vault $V                           # 所有项目当前阶段 / 接手 role / 是否已被认领
opc claim --role market --vault $V             # 领一条可开工的活 → 设当前项目 + 输出身份声明
opc claim --role market --project P002 --vault $V
opc release --role market --vault $V           # 释放，任务回到可领池
```

`claim` 会写任务池、设 `active_project`、把当前会话游标切到该项目，并直接打印本次身份声明（可贴进新会话）。若切换前原游标处于「待确认」，会先把回执归档到 `history`，不丢闸门。

### 23.4 两个会话并行（已支持）

**会话本身就是隔离单元**：single 模式下开两个会话、一个干 A 一个干 B；multi 模式下在同一个职业 Agent 下开两个会话分别干不同项目——都成立，前提是**每条命令显式带 `--project`**：

```bash
# 会话 A
opc claim --role market   --project P001 --vault $V
opc done  --role market   --project P001 --vault $V
opc go                   --project P001 --vault $V

# 会话 B（同时进行，互不影响）
opc claim --role strategist --project P002 --vault $V
opc done  --role strategist --project P002 --vault $V
opc go                   --project P002 --vault $V
```

交接状态已改为**每项目一份**：`99_Agent配置/_交接状态/P001.json`、`P002.json`…；旧 `_交接状态.json` 降级为「最近活跃」镜像，仅供 `opc handoff` 无参数时展示。`active_project` 只是**省略 `--project` 时的默认值**，不再是并行限制。

`opc done/go/handoff/queue/claim` 都按项目读写，两个会话各自写各自的状态文件，不会互相覆盖；闸门 0/2/7 也按项目独立拍板。`opc roster` 显示各职业在任务池里的认领，`opc queue` 显示各项目当前阶段与认领人。

## 29. 需求分诊与派活（`opc new --triage`）

**派活权在 `pm`，且只有 `pm` 有**。产品经理是整个项目的统领者：拿到需求 → 做需求分析 → 产出产品文档 → **由他决定这次要哪些岗位干活、各自产出哪些资产**。判定依据是**本次需求与各岗位的关联性**，不是「本次属于哪一类改动」——系统**不预设**任何固定类型枚举。

### 29.1 派活清单是路由的唯一真相源

写在 `4_产品基线.md` 的 `## 本次涉及岗位与产出资产清单` 小节，格式固定：

```markdown
## 本次涉及岗位与产出资产清单

| 岗位 | 本次是否涉及 | 产出资产 | 分诊理由 |
|---|---|---|---|
| design | 涉及 | 5_设计交付.md、5_原型.html | 改首页三处视觉，需要新视觉稿 |
| engineer | 涉及 | 6_实现与测试.md | 组件样式要落地 |
| architect | 不涉及 | — | 交互结构没变，接口不动 |
| growth | 不涉及 | — | 不涉及新版本发布 |
```

- 「本次是否涉及」写 `涉及` / `不涉及`；「产出资产」点名到具体文件；「分诊理由」必填。
- **可派任意岗位组合**（design+engineer+architect 三个都要也行，只派一个也行）。
- **零岗位**：本次确实不需要任何岗位投入时，在表下方写「零岗位：<理由>」。

### 29.2 命令

```bash
# 按 pm 派活清单建项（路由只看这份清单）
opc new 页面微调 --triage "30_项目/P001_某项目/4_产品基线.md" --from P001

# 变更性质只是标签，不决定谁干活；与 pm 清单冲突时以 pm 为准并报出差异
opc new 接口迭代 --scope 后端 --triage <基线文件> --from P001
```

| 参数 | 作用 |
|---|---|
| `--triage <文件>` | pm 派活清单路径（相对路径按当前目录与 vault 根解析）。**不给则走全量流程** |
| `--scope <性质>` | 变更性质标签：画面 / 后端 / 前端 / 文案 / 数据 / 迭代 / 其他 / 全量。**只写进 `_项目关系.md` 供检索溯源，不决定派活** |
| `--light` | 兼容别名，等价 `--scope` |
| `--from <PXXX>` | 继承上一版项目的 pm 分诊结论 |

### 29.3 生成结果

- 只生成 pm 点名的资产，**不硬凑全套**；无关岗位不产出、不执行、不生成文件。
- 交接链**按派活跳过**：`opc done` / `opc go` 推导下一棒时跳过本次未派活的岗位，通知里会列明跳过了谁；未被派活的岗位报完成一律被拒。
- 零岗位项目：**不建交接链、不发通知**，只在产出索引记一行（状态=已归档，关联规则列留分诊理由），流程直接走完。

### 29.4 与旧版的差异（v2.4 → v2.5）

v2.4 曾按六个固定类型路由（画面→仅 design、后端→architect+engineer、前端→design+architect+engineer、文案→仅 pm、数据→pm+architect+engineer、全量→完整流程），由**使用者选类型**代替 pm 判断。v2.5 取消这套枚举：**派活只看 pm 的清单**，`--scope` 降级为标签。

## 32. 云端仓库：本地写完再同步一份，并可从云端读（v2.7）

> **定位**：飞书 = **远程仓库**，而且是**带项目管理能力的远程仓库** —— 可沉淀**知识库、产品原型、各项目任务与需求**。创始人从云端查知识、拿未完成任务，回来在本地用 Agent 干活。
> **本地照常写入，工作流一个字都不改**；本地 Vault 始终是唯一真相源（宪法 §15.8）。云端是副本与入口，不是真相源。

### 32.1 命令

| 命令 | 作用 | 改本地？ |
|---|---|---|
| `opc sync` | **push（默认）**：把本地产出再写一份到云端 | 只读本地 |
| `opc sync status` | 比对本地与云端差异（按 hash / 修改时间） | 只读本地 |
| `opc sync init` | 在云端建 `OPC/` 目录，回显 token | 只读本地 |
| `opc sync tasks [--query 词] [--limit N]` | **拉云端各项目的未完成任务 / 需求** | **否（只读云端）** |
| `opc sync search --query 词 [--limit N]` | **搜云端沉淀的知识库 / 产品原型** | **否（只读云端）** |
| `opc sync pull --allow-restore` | 云端 → 本地覆盖 | **是**，必须显式加参数 |

**只有 `pull` 会写本地，且默认拒绝** —— 正常用法是「本地写 → 同步到云端」，反向覆盖容易用旧版本盖掉新的本地产出。

### 32.2 触发时机：初始化时问一次，之后按模式走（v2.7）

**`opc init` 时会问一次**：

```
── 云端仓库（可选） ──
用途：把项目托管到一个远程仓库（如飞书），并可沉淀知识库、产品原型、各项目任务。
      本地照常写入、工作流不变；配了之后产出落盘会自动同步一份到云端。
是否配置云端仓库（当前后端：飞书 CLI / 自定义外部 CLI）？输入 y 配置，其它键跳过：
```

**配了** → `sync_mode=auto`，之后每次产出落盘**直接同步，不再逐次问**。
**没配** → 保持 `ask`（每次问一次）或 `off`（完全不碰云端），随时可 `opc sync` 手工推。

> 初始化时配了，就说明确实要用 —— 所以 auto 模式**不再逐次询问**。

### 32.3 配置

在 `opc.config.json` 的 `backends.feishu` 里：

```json
"feishu": {
  "cli": "lark-cli",
  "folder_token": "<云端根文件夹 token>",
  "project_prefix": "OPC",
  "sync_mode": "auto",
  "enabled": true
}
```

| 字段 | 说明 |
|---|---|
| `cli` | 云端 CLI 可执行名，默认 `lark-cli` |
| `folder_token` | 云端根文件夹 token；**留空则同步静默跳过**（不阻塞流程） |
| `project_prefix` | 远端项目目录前缀，默认 `OPC` |
| `sync_mode` | `auto`（自动同步，不再问）/ `ask`（每次问一次，默认）/ `off`（不碰云端） |
| `enabled` | 置 `false` 可完全关闭同步 |

**拿 token**：`lark-cli drive files list` 看根目录，或 `lark-cli drive +create-folder --name OPC` 建一个并取返回的 token。

**认证**：飞书 CLI 需先完成授权 —— 执行 `lark-cli config init --new`，它会输出一个验证链接，用浏览器打开完成。凭证值不写入配置。

### 32.4 实现说明

- 同步桥 `opc-team/scripts/sync_feishu.py` 直接调用官方 `lark-cli` 的 `drive` 域（`+push` / `+status` / `+pull` / `+create-folder` / `+search`）与 `task` 域（`+search --completed false`），**不自己造轮子、不预设厂商私有接口**。`init` 会把它复制到 Vault 的 `99_Agent配置/通知桥/`。
- **`tasks` / `search` 是只读动作**：不需要 `folder_token`，**不改本地任何文件**；`tasks` 用 `task +search --completed false` 取未完成任务，`search` 用 `drive +search` 检索云端知识库与原型。
- **Windows 注意**：飞书 CLI 通常是 `lark-cli.CMD` 批处理文件，Python 的 `subprocess` 直接执行会报 `WinError 2`，必须经 shell 调用。桥脚本已统一用 `shell=True` + 引号包裹，Windows / macOS / Linux 通用。
- **不会误删云端**：底层 `+push` 不带 `--delete-remote`，云端多出来的文件不会被清理；远端目录结构自动镜像复用。
- **降级不阻塞**（§15.12）：未配 token / 未装 CLI / 未认证 → 只提示，流程照走。

## 33. 阶段 7 两段制：获客准备不等代码（v2.7）

> **阶段编号与 9 步工作流不变**，只是把阶段 7 内部拆成两段，解除「必须代码做完才能准备获客」的时序耦合。

| 段 | 内容 | 前置 | 能否在阶段 6 编码期并行 |
|---|---|---|---|
| **7a 发布前准备** | 渠道选定、素材清单、活动规则、ASO 关键词、FAQ、客服话术与升级路径、投诉入口、已知缺陷与观察指标 | `3_BRD.md` 指标口径 + 透传的分发渠道假设 / 验证预算 | **可以** |
| **7b 发布与验证** | **创始人执行**：发布、灰度放量、回滚决策、具体平台投放与推广跟进<br>**Agent 辅助**：出「创始人执行清单」（逐步骤带判定阈值）、事后采集真实用户数 / 留存 / 反馈、出「继续 / 转向 / 停掉」建议 | 可运行版本 + `## 上线与回滚` 就绪 + 闸门拍板 | 否 |

**为什么可以提前**：获客策略早在**阶段 0 / 1 / 3 就已钉扎** —— `0_约束卡` 的 `分发渠道假设` → `1_MRD.md` 的「用户聚集渠道 / 触达路径」 → `3_BRD.md` 的「获客渠道与冷启动成本」。素材与话术准备**不依赖代码**。

**不变的红线**：
- 7a 只出方案与素材，**未拍板闸门不得对外发布**、不采集真实数据
- 对外文案无绝对化用语 / 无效果承诺 / 无未脱敏信息
- 每个获客动作对应 BRD 中 ≥1 个成功指标，口径一致不改
- 7b 复用 7a 已定渠道与素材，不重复推翻已定策略

**分工不变（v2.8 明确）**：灰度执行、回滚决策、具体平台投放与推广跟进**始终由创始人执行**——这些需要真账号、真发布权、真投放，**不是 Agent 能做的事**。`growth` 只出策略、素材、话术与**创始人执行清单**，**不代为执行、不得声称自己已发布 / 已灰度 / 已投放 / 已获得用户**。

## 34. 产品经理推进进度：`opc advance`（v2.8）

> 创始人原话：「我写完之后就跟产品经理说，这个完成了，然后你就可以去在项目管理里面把这个进度给推进嘛。因为现实世界产品经理就是干这活的。」

### 34.1 用法

```bash
opc advance                  # 推进当前项目到下一棒
opc advance --project P001   # 指定项目
```

### 34.2 行为

| 步骤 | 动作 |
|---|---|
| 1 | 检查交接状态必须为「待确认」（没人报完成则拒绝） |
| 2 | **只推进一棒**，不跳步（§15.9 一阶段一通知） |
| 3 | 打印下一棒的角色、必读文件与跳过名单，并输出下一棒的身份声明 |

### 34.3 与 `opc go` 的区别

| | 谁执行 | 何时用 |
|---|---|---|
| `opc go` | **创始人**自己确认 | 创始人就在场，直接推进 |
| `opc advance` | **产品经理**代为执行 | 创始人口头告知「这个完成了」，由 pm 去项目管理里推进 |

**两者推进语义完全一致**，不新增机制、不改状态机。

### 34.4 闸门例外（重要）

阶段 0 / 2 / 7 是**人工闸门**，拍板权在创始人手上。闸门未拍板时 `opc advance` **拒绝推进**（rc=2）、**把「待拍板」落盘**、**推送待拍板通知**，并提示：

```
阶段 7 是**人工闸门**，需创始人给结论：通过 / 驳回 / 需补充。
  创始人确认后执行：opc go --decision 通过
  （产品经理推进的是「进度」，闸门拍板权始终在创始人手上，§7）
  已落盘「待拍板」（gate_stage=7）并推送通知：local · 已写入 99_Agent配置/_交接通知.md
```

**产品经理不得替创始人宣布闸门通过。**

落盘字段（`99_Agent配置/_交接状态/PXXX.json`）：

| 字段 | 含义 |
|---|---|
| `gate` | 该阶段是否为人工闸门 —— 由 `opc done` 写入，是**闸门口径的唯一真相源** |
| `gate_stage` / `gate_wait_at` | 等拍板的是第几阶段 / 从什么时候开始等 |
| `decision` | 拍板结论：通过 / 驳回 / 需补充（**「通过」也记**，v2.11） |
| `decided_by` | 拍板人（创始人） |
| `decided_at` | 拍板时间（ISO） |
| `decision_basis` | 拍板依据（`opc go --basis`，可选） |
| `decided_via` | 拍板通道（`opc go`） |

**v2.11 口径修正**：`opc pm` 台账与 `opc queue` 的「待人工闸门」此前按「**下一个**阶段号 ∈ gates」现算，而 `opc done` 按「**刚完成的**阶段」判定——两者差一格，导致**该拍板的项目漏报、不该拍板的误报**。现统一以交接状态的 `gate` 标记为准。

### 34.5 pm 的推进职责（岗位卡 §11.7b）

pm 岗位卡新增贯穿全程的推进职责：§1 定位、§2 所属阶段、§8 验收标准、§11.7b 四步流程、§11.9 自检条目；`opc role pm` 的身份声明提示词同步。

## 35. 增量同步 + 远程写入权归 pm（v2.10 · 范围隔离的收敛形态）

创始人先说「**每一个职业……他自己都可以去调用 CLI，只是更新他自己对应的东西而已**」，
后又补充并收敛：「**他呢，他就不能去改远程飞书的东西的这些状态的同步，统一交给 PM 去做**
……**每一次需求给到来都是一个时间戳，或者说一个版本号吧，这样子的话，我只要更新到新的版本号就行了呀，
就推到新的一个时间戳或者说版本号同步上去就好了呀，就做一个增量同步吧。**」

所以最终口径是两条：**远程写入权唯一归 pm** + **同步走增量版本目录**。

v2.9 的「范围隔离」在这一版收敛成更硬的形式：**范围隔离从「按角色分目录互不覆盖」
升级为「远程写入权只归 pm + 每次产出一个版本目录」**——不只是分目录，而是连碰远程的资格都收拢了。

### 35.1 两件事，各有各的边界

| | 谁做 | 做什么 | 碰远程吗 |
|---|---|---|---|
| **登记待同步** | **每个职业自己**（含 pm） | 把本岗本次产出**入队**（批次号 + 时间戳 + SHA256 + 版本号） | **否** |
| **推送队列** | **只有 pm** | 逐条推到远端，每个批次落一个**版本目录** | 是 |

**其它岗位一律不连远程仓库。** 这就是「不会太乱 / 飞书不会混乱」的机制保障——
不是靠约定，是靠**权限边界**：他们碰不到远程。

### 35.2 各岗怎么登记待同步

```bash
# 干完自己这一步后（推荐）
opc done --role design --sync-self

# 等价入口
opc sync --role design
```

效果：**只在本地写一条队列记录**（`30_项目/_同步队列/<批次号>.json`），不碰远程。
队列条目含：批次号（= 增量版本号）、项目号、岗位、入队时间戳、状态、
每个资产的相对路径 / SHA256 / 字节数 / frontmatter 版本 / mtime。

**入队范围 = 本岗本次产出的资产（主产出 + 附带资料）+ 本岗职业简历 + 本岗知识资产**。
**增量语义：每次产出只登记本次新内容，不重推本岗历史产出。**

### 35.3 pm 怎么推送

```bash
# 只读查看队列（纯本地，不需要 token）
opc sync --queue

# 推送队列（只有 pm 做）
opc sync --flush
opc sync --flush --project P001     # 只推某个项目

# opc advance 推进时顺带推送本项目队列
opc advance --project P001
```

**增量语义**：每个批次推到远端一个**独立版本目录**：

```
OPC/
└── P001/
    └── design/
        ├── S-20261114-112919-4AF6/     ← 第 1 次产出
        │   └── 30_项目/P001_x/5_原型.html
        └── S-20261114-143052-B71C/     ← 第 2 次产出（新版本目录）
            └── 30_项目/P001_x/5_原型.html
```

**历史版本全部保留、互不覆盖**——能看清每次产出的演进轨迹，不会越同步越乱。

### 35.4 降级与边界

- 未配 token / 未装 CLI / 未认证 → **只提示、不阻塞**，队列条目留在本地等下次（§15.12）。
- 推送失败的条目**状态不变**（仍是「待推送」），下次 `--flush` 自动重试。
- 队列条目里的文件若已被删除 → 推送时跳过该文件，其余照推。
- **本地 Vault 始终是唯一真相源**（§15.8）；云端是副本与入口，**不得**用云端覆盖本地。

### 35.5 `opc pm`：产品经理的多项目统筹台账（只读）

台账新增「**待推送**」列，显示每个项目有多少条队列待推。

### 35.6 修了一个边界 bug

产出索引里的 URI 形如 `local://30_项目/<项目>/<版本目录>/<role>/0_约束卡.md`，
此前当普通路径解析，导致**本岗产出取不到**（入队只拿到简历）。现剥离协议头。

### 35.7 不变的部分

9 步工作流、阶段编号、owner 边界、`gates`（0/2/7）原样未动；**本地照常写入不变**；
云端仓库定位（远程仓库，非真相源 / 非备份仓）与 `sync_mode` 三档口径不变；
闸门拍板权始终在创始人手上。

### 35.8 岗位卡口径

- **pm 卡**：§1 / §2 / §6 / §7 / §8 / §9 / **§11.7b 的 B 段（远程写入 + 增量同步对照表）** / §11.9。
- **其余 7 份**：§6「**同步授权（v2.10）**」改为「只本地入队」；deny 改为「**直接写远程仓库**」。---

## 36. 增量同步队列：完整操作手册（v2.10）

§35 讲的是**为什么**这么定；本节是**照着做**的操作手册。

### 36.1 队列长什么样

**位置**：`<Vault>/30_项目/_同步队列/<批次号>.json`（一条队列 = 一个文件）。
这是「待推送」的**唯一台账**——本地想推什么，全看这个目录。

**批次号即增量版本号**，格式 `S-<YYYYMMDD-HHMMSS>-<4位随机HEX>`，例如 `S-20261114-112919-4AF6`。
它同时出现在三处，保证可追溯：队列文件名、队列条目 `batch` 字段、远端版本目录名。

**队列条目字段**：

| 字段 | 含义 |
|---|---|
| `batch` | 批次号 = 增量版本号 |
| `project` | 项目号 |
| `role` | 产出岗位 |
| `queued_at` | 入队时间戳（ISO 8601，秒精度） |
| `status` | `待推送` / `已推送` |
| `remote_version` | 远端版本目录名（= `batch`） |
| `assets[]` | 每个资产：相对路径 / SHA256 / 字节数 / frontmatter 版本 / mtime |
| `pushed_at` | 推送完成时间（推之前为空） |
| `pushed_by` | 推送者（固定 `pm`） |
| `remote_path` | 实际落地的远端路径 |

**资产条目**里的 `sha256` 是内容指纹，`version` 取产出文件 frontmatter 里声明的版本号——
两者合起来保证「推上去的是哪一版」可校验、可回溯。

### 36.2 四条操作线（谁在什么时候跑什么）

| 命令 | 执行者 | 碰远程 | 作用 |
|---|---|---|---|
| `opc done --sync-self` | **任何岗位** | 否 | 把自己**本次刚产出**的资产入队 |
| `opc sync --role <role>` | **任何岗位** | 否 | 等价入口；按产出索引取本岗资产入队 |
| `opc sync --queue` | 任何岗位 | 否 | **只读**打印队列台账（不需要 token） |
| `opc sync --flush` | **只有 pm** | **是** | 逐条推送待推条目 |
| `opc advance` | **只有 pm** | **是** | 推进项目状态，**顺带**推本项目队列 |

### 36.3 各岗标准动作（写完这一步之后）

```bash
opc done --role design --sync-self
```

输出示例：

```
── 增量同步入队（本地） ──
批次：S-20261114-112919-4AF6（版本号 / 时间戳：2026-11-14T11:29:19）
本岗资产：2 份 → 待推送
  · 30_项目\P001_x\5_原型.html
  · 99_Agent配置\履历\design.md
  远端版本目录（由 pm 推送时创建）：OPC/P001/design/S-20261114-112919-4AF6/
  说明：本岗**不直接写远程仓库**；等 pm 执行 opc advance / opc sync --flush 时推送。
```

**关键**：输出里明确写着「不直接写远程仓库」——这条是权限边界的可见化，不是提示语。

**入队范围**（增量语义）：主产出 + 附带资料 + 本岗职业简历。
**不重推本岗历史产出**——每次只登记本次新内容。

### 36.4 pm 标准动作（推进这一步的时候）

```bash
# 1) 先看一眼队列（只读，可选）
opc sync --queue

# 2) 推进 + 顺带推送本项目队列
opc advance --project P001
```

`opc advance` 的推进语义与 `opc go` **完全一致**（只推进一棒、不跳步、闸门仍由创始人拍板），
只是额外多做一件事：把本项目待推条目推到远端。**推送失败不阻塞推进**（§15.12），
失败条目留在队列里等下次重试。

需要单独推送时：

```bash
opc sync --flush                  # 推全部待推条目
opc sync --flush --project P001   # 只推某个项目
opc sync --flush --dry-run        # 只演练不真推
```

### 36.5 远端最终结构

```
OPC/                              ← project_prefix（可配）
└── P001/                         ← 项目号
    └── design/                   ← 岗位
        ├── S-20261114-112919-4AF6/    ← 批次 1（历史保留）
        │   └── 30_项目/P001_x/5_原型.html
        └── S-20261114-143052-B71C/    ← 批次 2（新增目录，不覆盖批次 1）
            └── 30_项目/P001_x/5_原型.html
```

三层目录含义固定：`<前缀>/<项目号>/<岗位>/<批次号>/<相对路径>`。
**同一岗位的多次产出 = 多个并列批次目录**；**不同岗位之间路径天然隔离**，
不存在两个岗位写同一路径的可能——这就是「不会混乱」的结构性保证。

### 36.6 失败了怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示未配置云端根文件夹 token | 没跑过 `opc sync init` | `opc sync init` 拿 token，填进 `opc.config.json` → `backends.feishu.folder_token` |
| 推送失败但本地已落盘 | CLI 未认证 / 网络问题 | **不影响流程**；条目留在队列，下次 `--flush` 自动重试 |
| 队列里有条目但资产文件被删了 | 本地产出被清理 | 推送时**跳过该文件**，其余照推 |
| 队列条目状态一直是「待推送」 | 还没推 / 推失败 | `opc sync --queue` 看列表 → `opc sync --flush` 重推 |

**降级原则**：任何同步问题**只提示、不阻塞**。本地 Vault 始终是唯一真相源（§15.8），
云端推不上去，最多是「远程看不到」，本地流程照跑不误。

### 36.7 与 v2.9 的差异（迁移说明）

v2.9 是「各岗可直接连远程推自己那部分 + 远端按角色分目录」。
v2.10 改成「**各岗只本地入队 + 远程写入权唯一归 pm + 增量版本目录**」。

| | v2.9 | v2.10 |
|---|---|---|
| 各岗能否连远程 | **能** | **不能**（只本地入队） |
| 远端目录 | `OPC/<role>/` | `OPC/<项目号>/<role>/<批次号>/` |
| 远端同岗位多次产出 | 覆盖 | **并列版本目录，历史全保留** |
| 远程写入者 | 各岗 + pm | **只有 pm** |
| 状态推进者 | pm | pm（不变） |

**升级无需迁移数据**：v2.9 已推到远端的内容留在那儿不动；v2.10 起新产出走版本目录。
本地队列目录首次使用时自动创建。

### 36.8 边界红线

1. **其它岗位禁止直接写远程仓库**（含 `opc sync --all`、手动跑 CLI）。
2. **禁止跳过队列直接覆盖远端**——远端路径必须带批次号层。
3. **禁止用云端覆盖本地**（`pull` 仍需显式 `--allow-restore`，§32）。
4. **本地 Vault 始终是唯一真相源**，云端是副本与入口。
5. **闸门拍板权始终在创始人手上**——pm 代为执行推进，不等于 pm 能替创始人拍板。

## 37. 跨宿主安装与斜杠命令（宿主无关）

### 37.1 命令是独立提示词文件，不是脚本

`commands/opc/*.md` 每个文件 = 一个斜杠命令 = 一段**自洽的操作提示词**。宿主把它注入上下文后，Agent 按里面的步骤调用 `scripts/opc.py`。

- 文件名去掉 `.md` = 命令名的一部分：`init.md` → `/opc:init`。
- 目录名 `opc/` = 命名空间，多数宿主渲染成 `/opc:init`，部分渲染成 `/opc/init`——**两种写法指同一个命令**。
- frontmatter 只用三个通用字段：`name`（显示名）、`description`（何时用）、`argument-hint`（参数提示）。不用任何宿主私有字段，因此同一份文件在 CodeBuddy / Claude Code / Cursor 等宿主都能直接用。
- **每个命令只加载自己那一个文件**，不连带加载 SKILL.md 全文——这是「按需加载、不卡顿」的关键。

### 37.2 宿主目录候选

| 宿主 | 项目级 | 用户级 |
|---|---|---|
| CodeBuddy | `<项目>/.codebuddy/commands/opc/` | `~/.codebuddy/commands/opc/`（官方文档已确认） |
| Claude Code | `<项目>/.claude/commands/opc/` | `~/.claude/commands/opc/` |
| Cursor | `<项目>/.cursor/commands/opc/` | — |
| 其它 | 查该宿主的自定义命令目录，把 `opc/` 子目录放进去 | — |

> 层级差异：**用户级 = 所有项目都能用**；**项目级 = 只在本工作区可见**。CodeBuddy 官方文档只确认了用户级，项目级可用但若 `/` 列表不出现，改用用户级。

**其它任何宿主**（Cursor、Windsurf、Cline、Aider、OpenHands、某个自研 Agent……）：找到它的「自定义命令 / 自定义斜杠命令」目录，把 `opc/` 子目录放进去即可——**命令名与内容完全一致**，脚本路径按 §37.4 定位。若它连自定义命令都没有：把 `commands/opc/*.md` 的正文贴进它的提示词 / 规则文件，或按 §37.4 直接调 `opc.py`，效果一致。

### 37.3 一键安装

**通用装法（与宿主无关）**：本包**就是一个文件夹** —— ① 技能本体 = 把整个 `opc-team/` 文件夹放进**你的宿主认的技能目录**即可生效；② 斜杠命令 = 把 `commands/opc/` 放进**你的宿主认的自定义命令目录**。宿主不认目录名就查它的官方文档，或用下面的脚本（脚本只认你给的路径，不猜）。**不需要斜杠命令也能用** —— 直接说人话，Agent 加载技能后按 `SKILL.md` 的 Commands 表调 `opc.py`（见 §37.5 第 2 条）。

```bash
# 自动检测已存在的宿主目录并安装（内置几个常见宿主的快捷候选）
python scripts/install_commands.py

# 先看会装到哪
python scripts/install_commands.py --list

# 手动指定最终目录（任意路径都行 —— 换成你的宿主实际目录）
python scripts/install_commands.py --target "<宿主的命令目录>/opc"

# 连 skill 包一起搬到别的机器（装进宿主的技能目录）
python scripts/install_commands.py --copy-skill "<宿主的技能目录>"
```

安装脚本特性：幂等（同名 `.md` 覆盖）、只写 `.md`、不删任何东西、不猜盘符；带 `--dry-run` 可先看结果。

### 37.4 任意宿主：脚本路径怎么定位（四级查找，与宿主无关）

命令文件里只写 `<skill包目录>/scripts/opc.py`，**不出现任何宿主名**。定位顺序：

1. **环境变量 `OPC_SKILL_DIR`** —— 指向包目录；用户或部署脚本设一次，全局生效。
2. **宿主注入的 skill 目录变量** —— 指向包目录本身或其父目录。
3. **目录结构约定** —— `<本命令文件所在目录>/../../skills/opc-team/`：多数宿主把 `commands/` 与 `skills/` 放在同一配置根下，`commands/opc/x.md` 的上两级就是那个根。
4. **文件搜索** —— 在工作区与用户主目录搜 `opc-team/scripts/opc.py`。

拿到绝对路径后，用**宿主环境里可用的 Python 解释器**以绝对路径调用：

```bash
python3 <skill包目录>/scripts/opc.py status --vault ./OPC-Vault
```

`install_commands.py --print-script-path` 直接打印这个绝对路径，可贴进任何宿主的配置、脚本或 `OPC_SKILL_DIR` 环境变量。

### 37.5 宿主不支持 commands 目录怎么办

1. **最省事**：把 `commands/opc/<name>.md` 的正文**粘进该宿主的自定义命令 / 提示词功能**，命令名自己起（如 `opc-init`）。文件内容不依赖任何宿主语法。
2. **只要能力不要命令**：直接说「按 opc-team 建项目」，Agent 加载 skill 后会按 `SKILL.md` 的 Commands 表调 `opc.py`——效果等价，只是不出现在 `/` 列表里。
3. **换宿主时唯一要改的是路径**：命令里 `<skill包目录>` 指向宿主安装 `opc-team` 的位置（CodeBuddy `~/.codebuddy/skills/opc-team`、Claude Code `~/.claude/skills/opc-team`……）；**业务逻辑、命令名、行为完全一致**。

### 37.6 路径解析规则

- 脚本在 **skill 包内**（`<skill包目录>/scripts/opc.py`），与工作目录无关；`--vault` 指向 Vault（默认 `./OPC-Vault`）。
- 命令里的 `<skill包目录>` 由宿主决定，**每次新会话重装/搬家后只需确认这一处**。
- Python 解释器用宿主环境里可用的那个（本机路径见该机 `AGENTS.md`），不要用 PATH 上的占位程序。

## 38. 派活入口：清单落点、报错口径、副本体检（v2.12）

### 38.1 派活清单放在哪

| 形态 | 路径 | 说明 |
|---|---|---|
| 机器可读（**唯一真相源**） | `<项目目录>/_派活清单.json` | 路由只读它；改它 = 改派活结论 |
| 人可读 | `<项目目录>/_派活清单.md` | 与 JSON 同目录，同一份清单的两种形态；不要单独改它 |
| 回写小节 | `<项目目录>/4_产品基线.md` 的 `## 本次涉及岗位与产出资产清单` | **仅当该文件存在时**才回写（pm 参与的项目才有） |
| 待建区（项目还没建） | `99_Agent配置/_派活清单/<项目号>.json` | `opc new --triage` 建项成功后**自动搬进项目目录** |

> 待建区存在的意义：以前 pm 起草清单只能写个临时 md，路径记不住、下次找不到。现在清单**永远落在 Vault 内**，不散落在任意临时目录。

### 38.2 `opc triage`：pm 起草派活清单

```bash
# 派活给 design
python scripts/opc.py triage --project P001 --role design \
    --assets 5_设计交付.md,5_原型.html --reason "改首页三处视觉" --vault <Vault>

# 明确「不涉及」
python scripts/opc.py triage --project P001 --role architect --involved no --reason "接口不动" --vault <Vault>

# 判定零岗位
python scripts/opc.py triage --project P001 --zero --reason "本次只修文案口径" --vault <Vault>

# 只读查看
python scripts/opc.py triage --project P001 --show --vault <Vault>
```

规则：

- `--reason` **必填**（派活和零岗位都要写）——它是事后复盘的依据；漏写直接报错。
- `--assets` 用逗号或顿号分隔；写 `5_设计交付.md` 时系统会自动去掉扩展名作为产出键。
- `--involved` 只认 `是/否`（`yes/no`）；省略按「涉及」处理。
- 岗位名必须在 `role_bindings` 里登记，否则报错（不静默跳过）。
- 命令**可多次调用**，同岗位后写覆盖先写（逐岗位追加最省事）。

### 38.3 清单解析失败：显式报错，不再静默降级

**旧行为（v2.11 及以前）**：`opc new --triage <文件>` 解析不出内容 → 静默走全量 9 步 → 8 个岗位全派。创始人毫不知情。

**新行为（v2.12）**：

| 情况 | 结果 |
|---|---|
| 显式给了 `--triage`，但找不到清单小节 | **报错并中止建项** |
| 清单小节在，但没有一行判出「涉及」 | **报错并中止建项** |
| 「本次是否涉及」列写了不认识的词（只认 涉及/不涉及、是/否、✅/❌ 类） | **报错并中止建项** |
| 岗位名未在 `role_bindings` 登记 | **报错并中止建项** |
| JSON 格式坏 | **报错并中止建项** |
| 中止时的副作用 | **不留空项目目录壳**（目录在清单校验通过之后才建） |
| **不带** `--triage` | 仍按全量 9 步，但**明确打印提示**并给出只派部分岗位的做法 |
| 清单里写「零岗位」（正文声明或表格行均可） | **合法**，不算错 |

### 38.4 `opc pm` 的「现在该派谁」面板

口径 = **接手岗位（`step_owner`）× 岗位占用（任务池 claim）× 闸门状态（交接状态 `gate` 标记）**：

| 结论 | 含义 |
|---|---|
| 可接（该岗位现在空闲） | 可以立刻派活 |
| 进行中 | 该岗位已接手本项目 |
| 排队（该岗位正忙：某项目） | 该岗位被别的项目占着 |
| 冲突（该岗位同时被多项目需要 → 先排优先级） | **只提排期建议，不得替创始人定优先级** |
| 等创始人拍板 → 暂不派活 | 撞了人工闸门 |
| 待 pm 推进 | 收到通知后 `opc advance` |

`opc pm` 同时输出**派活清单状态**（每个项目有没有清单、清单里派了谁、更新时间）。

### 38.5 `scripts/check_sync.py`：多副本一致性体检

同一个包在机器上可能存在**多份副本**（开发源目录 / 项目级安装目录 / Vault 内文档副本），**彼此没有同步机制**——改了源目录，别处仍是旧的，就是「改了不生效」。

**默认扫描范围 = 本项目内**：只比对工作区内的副本（源目录 / 项目级安装 / Vault 文档副本）。工作区**外**（用户主目录下的全局技能目录）**默认不扫**——同步边界就在项目内，扫到外面的旧副本只会得到误报。需要时用 `--include-home` 显式打开。

```bash
# 自动发现本项目内的副本 + 比对（只读，不改任何文件）
python scripts/check_sync.py --vault <Vault>

# 额外扫用户主目录（默认不扫）
python scripts/check_sync.py --vault <Vault> --include-home

# 手动指定副本
python scripts/check_sync.py --extra <副本目录>

# 机器可读
python scripts/check_sync.py --json
```

- 退出码 `0` = 全部一致；`1` = 有差异；`2` = 参数错误。
- 副本定位四级（优先级从高到低）：`OPC_SKILL_DIRS` 环境变量 → `OPC_SKILL_DIR` 环境变量 → 目录结构约定（常见宿主目录名，**示例清单，不构成默认依赖**）→ 有界文件搜索（默认只扫当前工作区；用户主目录**仅在 `--include-home` 时**纳入）。
- 参与比对：`SKILL.md` / `VERSION.md` / `opc.config.json` / 宪法 / 手册 / `opc.py` / 8 份岗位卡 / 全部命令文件；传 `--vault` 时另比对 Vault 内的宪法、手册、岗位卡副本。
- **发现差异时**：把源目录的文件复制到对应副本（覆盖前先确认副本里有没有你自己的改动）。

## 39. 多会话并发安全 + 规则钉扎与版本漂移（v2.13 · P1 实证）

> 本节是 v2.13 P1「3 波次并行验证」的**实证结论**与随之而来的修正。自测：`scripts/selftest_parallel.py`（27 项断言）。

### 39.1 能并行什么，不能并行什么

| 资源 | 粒度 | 并行安全性 |
|---|---|---|
| 交接状态 `_交接状态/PXXX.json` | **按项目一份** | ✅ 不同项目互不覆盖（§23.4） |
| 产出文件 `30_项目/<项目>/V<N>/<role>/<资产>.md`（v2.20 起含 0_约束卡/1_MRD，全部随版本） | 按项目 + 版本 + 职业 + 资产 | ✅ 不同项目不重叠；**同项目不同职业各写各的目录，互不覆盖** |
| 产出索引（§15.8 唯一结构化出处） | **共享单文件** | ⚠️ 读改写必须加锁（v2.13 起） |
| 职业任务池 `99_Agent配置/_职业任务池.json` | **共享单文件** | ⚠️ 读改写必须加锁（v2.13 起） |
| 项目号 `Pxxx` | 全局唯一 | ⚠️ 必须原子占号（v2.13 起） |
| `opc.config.json` 的 `active_project` | **单游标** | ⚠️ 并行时是「最后写入者」的游标 —— 并行会话**必须显式带 `--project`** |

### 39.2 P1 实测发现的四个真实缺陷（已修）

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| ① | **并发认领丢记录** | 两个会话同时 `opc claim`，各自读到旧任务池 → 后写覆盖先写 → **一轮只认领成功 1 条**（实测复现） | 新增 Vault 级跨进程锁（`O_CREAT\|O_EXCL` 抢占 + 自旋重试 + 60 秒残留锁自动打破）；`claim` / `release` 的「读→改→写」整体进临界区 |
| ② | **读到写了一半的文件** | 并发写共享 JSON 时读者可能读到半截内容 → 解析失败 → 被静默当成「空池 / 空状态」 | 写入改为**原子写**（同目录临时文件 + `os.replace`），读者永远只看到完整版本；Windows 上目标被占用时短暂重试 |
| ③ | **并发建项撞项目号** | 两个会话各自算「下一个项目号」→ 拿到**同一个** `Pxxx` → 目录撞名 | 新增占号凭据 `99_Agent配置/_项目号.seq`：在锁内取号并落盘，**先占后干活**，号不重（中途失败留号段空缺 —— 编号只作标识，空缺可接受） |
| ④ | **项目标识两套形态混存** | 状态文件里 `project` 有时写 `P001`、有时写 `P001_甲项目` → `done` 的「项目不一致」校验误判 | **写入即归一**（状态文件统一存项目全名）+ **比较一律用项目号归一函数**（项目号与全名互认） |

> ① 的教训：并发缺陷**不会稳定复现**。第一次跑通不代表对 —— 必须连跑多次（自测脚本已连跑 8 轮验证）。

### 39.3 规则钉扎：钉「Vault 里真实存在的那份规范」

- §10 的 `pinned_refs` 此前取 `opc.config.json` 的**静态** `schema` 字段 —— 该字段只在 init 时写一次，**换包升版后老 Vault 仍写着旧版本号** → 新建项目会钉到一个 Vault 里**并不存在**的规范版本（实测：宪法已是 v2.13，新项目却钉 `OPC-架构规范@v2.12`）。
- v2.13 起：钉扎改按 **Vault 内宪法文件的实际版本**（读 `| 版本 | vX.Y |` 行），读不到才退回配置声明。
- `opc status` 现在把漂移**显式化**（原来只有一个来源，查不出来）：
  - `宪法实际 vX.Y` —— Vault 内宪法文件的版本；
  - `配置声明 vX.Y` —— `opc.config.json` 的 `schema`；两者不一致会明确报「版本漂移」；
  - `规则钉扎：N 个项目 | 钉在旧规范版本：…` —— 哪些项目还钉在旧版本。
- §10 口径**不变**：升级不自动改变在跑项目的依据，钉扎保持原值；重钉属「解钉」，先做 §11 变更影响评估，评估通过后用 `opc repin` 执行（§39.5）。

### 39.4 并发会话使用纪律

1. **每个并行会话都显式带 `--project`** —— 不要依赖 `active_project` 这个单游标。
2. **同一项目内仍然串行**（§15.3）：一个项目同一时刻只允许一个 Agent 在写。
3. **认领时挑不同项目**：`opc claim --role <role> --project Pxxx`，两个会话不要领同一项目的同一步。
4. 锁是**互斥 + 短临界区**，不是队列：等待超过 20 秒直接报错而不是无限排队 —— 刻意如此，避免「看起来在跑、其实卡在锁上」。
5. 锁文件 `99_Agent配置/.opc.lock` 是临时文件，正常结束即删除；**残留超过 60 秒会被自动打破**（持锁进程已死）。

### 39.5 重钉工具（`opc repin`）

§10 规定「解钉必须先做 §11 变更影响评估」—— 评估由人做，**执行**由脚本做，避免手改 frontmatter 改错行。

```bash
# 查看各项目钉在哪个版本（status 里也有一行汇总）
python scripts/opc.py status --vault <vault>

# 重钉（必须带评估结论作为留痕）
python scripts/opc.py repin --vault <vault> --project P002 --project P003 \
    --reason "§11 变更影响评估：未改动九步链 / 角色权限 / 闸门语义，产出依据不变；创始人已确认。"
```

| 参数 | 说明 |
|---|---|
| `--project PXXX` | 项目号或项目全名，**可多次**；默认只动点名的项目 |
| `--all` | 处理全部已钉扎项目（要动全部必须显式写出来） |
| `--to vX.Y` | 目标版本；默认 = **Vault 内宪法实际版本** |
| `--reason "…"` | **必填** —— §11 评估结论，写进项目 frontmatter 留痕 |

执行后项目 `0_约束卡.md` 会多几行留痕，并把 `updated` 更新为当天：

```yaml
pinned_refs: [[OPC-架构规范@v2.14]]
repinned_from: v2.13
repinned_at: 2026-11-15
repin_reason: "§11 变更影响评估：……"
repin_history: [{"from": "v2.13", "to": "v2.14", "at": "2026-11-15", "reason": "……"}]
```

**每次重钉都重写 `repinned_from` / `repinned_at` / `repin_reason`**（它们描述的是**最近一次**迁移），历次迁移追加进 `repin_history`。v2.14 之前这里有个失真：项目已有留痕时脚本整块跳过 → 二次重钉后 `pinned_refs` 已是新版本，留痕却还写着上一次的来源与结论。

**重钉只改「依据哪个版本」，不改已产出的内容** —— 产出本身仍按原依据保留（§10）。

## 40. 外部编排器（v2.14 · 收口「唯一硬缺口」）

> 脚本：`scripts/orchestrator.py`。自测：`scripts/selftest_orchestrator.py`（38 项断言）。

### 40.1 它补的是哪一步

现状（手册 §22 表格第 3 行曾标注为**唯一硬缺口**）：

```
opc done ──→ 创始人回一句「继续」──→ opc go ──→ 下一棒
                    ↑ 这一步全靠人盯着
```

编排器替掉的是**中间那句「继续」**——但**只在非闸门阶段**。闸门阶段那句是人**拍板**，不是流程推进，自动化不能代劳。

### 40.2 三条不可越界的边界

| 边界 | 编排器怎么做 | 为什么 |
|---|---|---|
| **不代拍闸门** | 阶段 0 / 2 / 7 遇闸门：落盘「待拍板」+ 推一条通知给创始人，**停下**，`decision` 字段一概不写 | 拍板权始终在创始人手上（宪法 §15 ④）；自动化一旦写 `decision`，§23.4 的「人工闸门」就形同虚设 |
| **不唤醒别的 Agent** | 交接只走固定文件落盘 + 通知通道；下一棒仍**自己领活**（`opc queue --role <role> --claim`） | §15.3 禁止 Agent 间对话内传递 / 互相 @ 唤醒 |
| **不跳步** | 只推进一棒，复用 `opc advance` 的状态机与校验 | §15.9 |

外加一条：**不改任何产出内容**——编排器只读 frontmatter 判断状态，不碰阶段文档。

还有一条：**已收尾的项目不再编排**（不推进、不提醒）。判据是**产出索引**里该项目的「状态」列 ==「已归档」（`opc close --archive/--link` 写入，零岗位项目建项即置）。

⚠️ **不要拿 `0_约束卡.md` 的 `status` 当项目级收尾信号**——那是**文档级**状态：阶段 0 的产出文档就是约束卡本身，阶段 0 跑完它会变成「已完成」，与「项目已收尾」同值同形。拿它判断会把**刚跑完阶段 0、正要推进的项目**永远跳过 —— 编排器直接失效（v2.14 实测踩过，见自测第 11 组）。

### 40.3 用法

```bash
# 跑一轮就退出（最常见：放进 cron / 外部调度器）
python scripts/orchestrator.py --vault <vault> --once

# 长驻轮询（默认 60 秒一轮）
python scripts/orchestrator.py --vault <vault> --interval 60

# 先看它会做什么，什么都不改
python scripts/orchestrator.py --vault <vault> --once --dry-run

# 机器可读输出
python scripts/orchestrator.py --vault <vault> --once --json
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--once` | 否（常驻） | 跑一轮就退出 |
| `--interval` | 60 | 轮询间隔秒 |
| `--min-wait` | 30 | 非闸门阶段：报完成后再等多少秒才推进（**给创始人留喊停窗口**） |
| `--remind` | 900 | 同一闸门 / 停滞的重复提醒间隔秒 |
| `--idle-timeout` | 1800 | 进行中多久无进展算停滞（只提醒，不推进、不打断） |
| `--channel` | 配置里的 `notify.channel` | 通知通道；`local` = 只写 `_交接通知.md` |
| `--project` | 全部项目 | 只处理指定项目 |
| `--dry-run` | 否 | 只报告不动作（不推进、不写任何文件） |
| `--max-rings` | 3 | 同一棒重敲门铃次数上限（v2.29）；超限升级提醒创始人，不再敲 |

### 40.4 幂等与并发

- **幂等**：推进靠**回执 token + 状态变化双重判定**（不靠退出码——校验失败与闸门都返回 `2`，靠退出码猜不可靠）；通知靠编排状态 `99_Agent配置/_编排状态.json` 去重。重复跑不会重复推进、不会重复通知。
- **不与锁嵌套**：Vault 锁**不可重入**（跨进程会互等到超时）。编排器因此**不自己写业务状态**——业务状态只由**子进程** `opc.py advance` 写；编排器只写自己的编排状态文件，写入进 `VaultLock`。
- **闸门落盘**：推进撞上闸门时，`opc advance` 自己落盘「待拍板」并推送通知（v2.11 起）——编排器只是识别出这个状态并停下。

### 40.5 拍板结论的归档（v2.14 修的第三个真实缺陷）

`opc go --decision 通过` 推进后，旧实现把 `decision` / `decided_by` / `decided_at` 留在状态**顶层**——于是**下一个闸门看着像「已经拍过板」**。自动化一旦只判「`decision` 在不在」，就会绕过创始人的拍板权。

现改为：**推进时归档进 `decisions` 历史列表并清空顶层**。

```json
{
  "status": "进行中",
  "stage": 3,
  "decisions": [
    { "stage": 2, "role": "strategist", "decision": "通过",
      "decided_by": "创始人", "decided_at": "2026-11-15T09:12:33",
      "decided_via": "opc go", "decision_basis": "…" }
  ]
}
```

历史带**阶段号** → 「事后查得出是哪个闸门、由谁、什么结论、依据是什么」（D4-2 诉求更强，不是变弱）。**驳回 / 需补充**不推进，顶层仍保留当次结论供下一棒看——这是有意的不对称。

### 40.6 编排器 vs 创始人：什么时候必须回到人

| 情形 | 谁来 |
|---|---|
| 非闸门阶段，某棒已报完成并通过校验 | **编排器**自动推进（可在 `--min-wait` 内喊停） |
| 人工闸门（阶段 0 / 2 / 7） | **创始人**：`opc go --project Pxxx --decision 通过 / 驳回 / 需补充` |
| 某棒久无进展 | 编排器只**提醒**；要不要催、换人，是人的决定 |
| 产出质量判断 | **人**——编排器只认「`opc done` 已通过校验」，不评价内容好不好 |

### 40.7 重敲门铃（v2.29）：叫了没人领活怎么办

v2.28 接上了门铃（`new` / `go` / `advance` 推进后 pm 会 @ 下一棒），但门铃**发完即忘**——
对方 bot 掉线 / 没看到，链就静默断掉。v2.29 补了闭环：

```
门铃已发 ──→ 下一棒 N 分钟内没 opc claim ──→ 编排器按 --remind 间隔重敲
             （已领活 / 间隔未到 / 敲满 --max-rings 次则不敲）
敲满 --max-rings 次（默认 3）──→ 升级「叫不醒」提醒创始人（每棒只升一次），不再敲
```

- **台账**：门铃每次**真正尝试**（成功或失败）由 `opc.wake_next_role` 记入
  `99_Agent配置/_编排状态.json` 的 `projects/<项目>/doorbells/<阶段>/<角色>`
  （`count` / `last_at` / `ok` / `detail`）；配置性跳过不记。
- **三护栏防重复骚扰**：① 任务池 `claims` 匹配项目+阶段 = 已领活，不敲（交给停滞提醒）；
  ② 距上次门铃不足 `--remind` 秒不敲（与闸门 / 停滞提醒同一去重模式）；
  ③ 每棒累计 `--max-rings` 次封顶。**最坏情况只是多一条 @ 消息**——防重复干活的是状态机
  （`done` 回执 token / `claim` 冲突检查），门铃只是叫醒信号。
- **性能**：每轮每个进行中项目只多做两次文件读；到点重敲才发飞书消息。
- **升级口径**：「叫不醒」通知只提醒创始人人工确认（群里直接 @ 该角色，或
  `opc release --role <role>` 换人），**编排器不代换人、不代派活**。
- 自测：`scripts/selftest_ring.py`（15 断言，开发期工具，不随包分发）。

## 41. 云端台账（v2.15）：表结构真相源与使用规矩

> **外部台账后端可替换**（飞书多维表格 / 钉钉多维表 / 其它），本节以**飞书多维表格**为已落地实例；口径、命令形态与「结构真相源在仓库」的做法对任何后端一致。

台账 = **云端协作面**（看进度、派活、随手改一行）；本地 Vault = **产出真相源**。两者用**同一套字段口径**对齐 —— 谁也不迁就谁。

### 41.1 三条定性（先读这段）

1. **台账是副本与入口，不是真相源**（宪法 §15.8）。本地文档说了算，**不得**用台账覆盖本地。
2. **表结构的真相源在仓库**：`scripts/base_schema.py`。改表 = 改这个文件 + 跑一次 `--apply`。**不要在飞书界面手改结构** —— 手改则仓库与线上漂移、无法 diff、无法回滚。
3. **写入权归 pm**。台账行由 pm 维护（新增棒、写「任务执行人」、推进「进展」）；其它岗位**只读**。

### 41.2 表 ↔ OPC 五层

| 台账表 | 一行 = | OPC 侧 |
|---|---|---|
| 项目汇总 | 一个项目 | `30_项目/PXXX/` |
| ①需求池（关联项目） | **一条需求（REQ）** | `4_功能清单.md` 的 `## 需求池` 小节 |
| ②版本开发计划 | 一根棒（一个任务） | 九步工作流里的一棒 |
| 发布版本 | 一个里程碑 / 版本 | 阶段 6 发布 |
| ③版本 Bug 记录 | 一个缺陷 | 缺陷登记 |

逐字段口径见 **宪法 §15.17.3**（台账列 ↔ OPC 侧对应 + 口径说明）。

### 41.3 命令

```bash
python scripts/base_schema.py --check            # 只读：仓库定义 vs 线上实际；退出码 0=一致、1=有差异
python scripts/base_schema.py --apply --dry-run   # 试跑：会加哪些列 / 补哪些枚举 / 换哪个枚举
python scripts/base_schema.py --apply             # 实写（改前自动备份到 .base_schema_backup/）
python scripts/base_clean.py --list              # 只读列出各表每行（带 record id）
python scripts/base_clean.py --apply --yes        # 清演示数据（先备份，只清 5 张业务表）
```

**台账地址从哪来**（v2.15.1 起**包内一律留空**）：

`app_token` 与 5 张表的 `table_id` 是**租户资源标识** —— 写进发布物等于让所有用户默认指向**别人的表**，一跑 `--apply` 就去改别人的数据。所以发布包里的 `opc.config.json` 这两项是空的，须自行指定，三种方式任选（优先级由高到低）：

1. **配置文件**：`<Vault>/opc.config.json` 的 `backends.feishu.base_token` + `backends.feishu.base_tables`（表名 → `table_id`）；用 `--vault <Vault>` 或 `--config <路径>` 指路。
2. **环境变量**：`FEISHU_BASE_TOKEN`；单表覆盖用 `FEISHU_BASE_TABLE_SUMMARY` / `_REQUIREMENTS` / `_PLAN` / `_BUGS` / `_RELEASES`。
3. **命令行**：`--base-token <token>`（单次运行，不落盘）。

**未配置时脚本直接报错退出（码 2），不会碰任何表** —— 这是刻意的：宁可不给用，也不给错对象用。

要点：

- **写操作边界**：只加列、只补枚举项；**不删列、不删行**。唯一整体替换白名单 = ②表「负责角色」（OPC 8 岗位 ↔ 模板 9 个通用研发角色；两套并存会让看板含义漂移）。替换前自动导出备份。
- **删行是另一个脚本**：`base_clean.py` 单独触发（真删必须显式 `--yes`），先备份记录快照再逐表删；模板自带的两张引导表不在范围内。
- **lark-cli 调用方式**：脚本**直调原生二进制**（`node_modules/@larksuite/cli/bin/lark-cli[.exe]`），不经过 npm 包装链 —— 包装链用 `stdio:"inherit"` 转发 stdout，被程序捕获时拿到的是**空串**，最易误判成「接口坏了」。
- **认证用用户身份**（`--as user`）；bot 身份缺多维表格权限，会报 `app_scope_not_applied`。

### 41.3.1 台账层级：顶层 = 需求版本，子级 = 任务（v2.20 创始人拍板）

**台账是两层结构，不是一层**：

| 表 | 顶层行（父链接为空） | 子记录（挂「关联父任务」字段） |
|---|---|---|
| **①需求池（关联项目）** | 一个**需求版本**一行：`需求编号` = `<短ID>-<版本>`（如 `P001-V1`）、`任务名称` = **版本台账「需求」列**的原文 | 该版本下的**任务**（阶段任务） |
| **②版本开发计划** | 一个**需求版本**一行：`版本键` = `<短ID>-<版本>`、`任务描述` = 版本需求名 | 该版本下的**阶段棒**（每阶段一根，含 OPC 阶段 / 负责角色 / 进展 / 拍板结论） |

**读法**：在飞书里看到「①需求池」的一行 `P001-V1`，它就是**一个需求版本**；它下面缩进的子记录才是这个版本里的各个任务。**不是**「每个功能一条顶层行」。

**为什么这么设计**：
- 一个项目版本 = 一个需求（§15.18.1「版本 = 一次立项」）。台账要能一眼看出「这个项目有哪几个版本、每个版本推进到哪」→ 顶层必须是版本。
- 功能条目（`REQ-PXXX-NN`）粒度更细，是**本地** `4_功能清单.md` 的内容；它们与版本的关系由「阶段棒」承载，不占台账顶层。
- 追加立项 V2 → 台账**多一行顶层**（`P001-V2`），V1 行保留不变（历史可见）。

**写台账的正确姿势**：
```bash
# 一键同步：本地真相源 → 台账（pm 专用；只读 _版本台账.md + _交接状态/，不猜状态）
python scripts/base_sync_status.py --vault <Vault绝对路径> [--project P001] [--dry-run]
```
- **幂等**：同一 `(版本键 / 需求编号, OPC 阶段)` 重复同步只更新不新建。
- **作废版本自动跳过**（台账里标「已作废」的版本不写行）。
- **进展判定**：当前棒按交接状态（进行中 / 待确认）；已完成的按**产出文件是否落盘且 `status` 非草稿**判（比索引状态可靠）。
- **无派活清单链的项目**（全量 9 步流程）→ 自动回退到 profile 的 `step_owner` 还原 9 步链。

**手写 lark-cli 时的两条硬约束**（实测踩坑）：
1. **link 字段的 CellValue** = `[{"id": "recXXX"}]`（不是 `{"record_id": ...}`）。
2. **不要用 `+record-upsert` 做批量更新**——它是**单条**（一次一条、字段顶层 map）；批量用 `+record-batch-update`，payload 形状是 `{"update_records": {"recId": {字段: 值}}}`。

**视图树形显示**：父子**数据**写好后，飞书网格视图仍可能平铺显示 —— 缺的是**视图属性** `hierarchy_config.field_id`（需指向自关联字段「关联父任务」）。OpenAPI 可设，但**必须 PATCH**（`PUT` 会 404）：
```python
from base_progress import ensure_hierarchy_config
ensure_hierarchy_config(vault, token, table_id, "关联父任务")
```
- ①需求池正常仅因**模板预置**了层级配置；②版本开发计划需要脚本补。
- 这是**宿主 UI 边界**而非代码缺陷——某些情况下仍需在飞书界面「子记录设置」里手动选一次「关联父任务」字段。

### 41.4 派活怎么用这张表

1. 创始人在线上群里 **@PM**（或直接给 PM 发消息）；
2. PM 判断派谁（例如 market），在 **②版本开发计划** 新增或更新一行：写「负责角色」= 该谁干、「任务执行人」= 实际接手人、「进展」= 可开工；
3. 被派岗位**自己去表里查活领走**（pull 式认领，§23.1 / §15.3）—— **不是别人 @ 它才动**；
4. 本地侧仍由 `opc claim` / `opc done` 推进，**本地状态为准**。

> **v2.15 不做行级自动同步**：OPC ↔ 台账之间不自动写行。台账行由 pm 在线维护，本地文档仍是产出真相源。双向同步需另立一版（v2.16）单独设计。

## 42. 版本链与知识沉淀（v2.17）

> 共识全文见 `docs/adr/0005-版本链与知识沉淀.md`；宪法条款见 **§15.18**。

### 42.1 一句话

**版本 = 一次立项**（创建项目 = V1；项目内确认「这个需求要做」= V2、V3…），**沉淀 = 各职业把自己这一版的经验写进自己的履历卡**。

### 42.2 版本链

```bash
# 看这个项目有几版
python scripts/opc.py version list --project 会员工具 --vault $V

# 追加一次立项 = 拿下一个版本号（版本号只增不复用，废号不回收）
python scripts/opc.py version new --project 会员工具 --需求 "把积分改成跨门店通用" --vault $V

# 这次要派哪些岗？给一份新的 pm 派活清单（缺省沿用项目上一版）
python scripts/opc.py version new --project 会员工具 --需求 "…" --triage ./4_产品基线.md --vault $V
```

| 事情 | 怎么做 | 结果 |
|---|---|---|
| 创建项目 | `opc new <项目名>` | 自动落 **V1**（台账 + 交接状态 `round=V1`） |
| 项目内追加立项 | `opc version new --需求 "…"` | 拿到 **V2 / V3…**；**只登记不产文件**（版本目录 `V2/` 建好，等岗位开工）；交接链按新版本重建，起点 = 新版本第一个被派的岗位 |
| 立项不带闸门 | 任何时候都能做 | 阶段 0/2/7 的闸门管的是「这一步能不能过」，不是「能不能开始做」 |
| 一个版本 ≠ 走完九步 | 派活清单说了算 | 派谁、走哪几步仍由 `pm` 决定（§29 / §15.14）；**没有清单才回退全量 9 步** |
| 缺 `--需求` | 报错，不占号 | 立项必须有需求描述 |

**版本台账**：项目目录内 `_版本台账.md`，一个版本一行（版本号 / 立项时间 / 本次需求 / 状态 / 产出份数 / 沉淀状态 / 沉淀时间）。它是版本链的**唯一真相源**，产出索引的「版本」列与它对应。

**文件命名与目录**（v2.18 起）：产出按「**版本目录 → 职业目录 → 资产**」三级落盘 —— `V2/design/5_设计交付.md`；版本号是**目录段**（文件名不带前缀）；**没干活的职业在该版本下连目录都不存在**。阶段 0 / 1 的项目级文档（约束卡、MRD 等）全项目一份，仍落**项目根**。详见宪法 §15.19。

### 42.2.1 产出按需生成（v2.18）

```bash
# 岗位开工：只生成自己那一份骨架（已存在则跳过）
python scripts/opc.py scaffold --role design --project 会员工具 --vault $V
```

- 建项 / 追加立项**不预生成任何空壳**：只写台账行 + 索引行 + 交接链。
- `scaffold` **只生成本项目该版本索引里登记的该岗资产**（派活项目 pm 只点名 `4_产品基线`，就只出那一份）。
- 流程：**scaffold → 填内容 → 改 `status` → `opc done`**。未落盘时 `opc done` 会拒绝并提示先 scaffold。

### 42.3 沉淀

```bash
# ① 派发：谁有实际产出 / 素材是什么 / 写到哪（不生成中间层文件）
python scripts/opc.py distill --project 会员工具 --vault $V

# ② 各职业自己写自己的履历条目（工具只写标题 + 骨架，正文自己写）
python scripts/opc.py link --project 会员工具 --version V2 --role design --vault $V

# ③ 汇总：谁写了 / 谁没写；齐了 → 版本状态 = 已沉淀
python scripts/opc.py distill --status --project 会员工具 --vault $V
```

- **触发靠口语**：创始人说「可以沉淀知识了」→ Agent 立即执行；Agent 也可反问「是不是要沉淀知识了？」。**不设审批流**。
- **粒度 = 当前最新版本的增量**：不是项目全量累计；同一项目可沉淀多次，条目**追加**不覆盖。
- **各岗自己写自己的**：工具**不代写**正文 ——「怎么落地的 / 坑与解法 / 结果」由本职业填。
- **没产出的岗不写**：`status: 草稿` 的占位空壳**不算产出**，`opc distill` 会把这类岗列在「无产出」里。
- **重复写跳过**：再写同一条会提示「已存在」；确需补写 → `--修改 "<说明>"`，**留痕**写进条目。
- **写入后回填**：产出索引该行的「简历条目」自动填成条目标题。

**落点**：各岗自己的 `99_Agent配置/履历/<role>.md`（C 节）。标题形如 `### 会员工具 · 2026-11 · V2`（**不带项目号**）。

## 44. 人话入口：创始人只说人话（v2.20）

> 细则单一真相源：`assets/人话入口.md`；本节是手册侧的索引与口径。
> 动机：命令是**内部实现**，创始人不该背命令；但「人话 → 命令」的映射如果只写在某个工作区的 `AGENTS.md` 里，就**没有可分发性** —— 别的用户装上 Skill 后是残的。映射必须住在**包里**。
> 但**不能住在宿主入口文件里**（那是抄本，见 §44.6）。

### 44.1 三层落点（谁装都等价）

| 层 | 载体 | 谁读 | 作用 |
|---|---|---|---|
| 规则层 | `SKILL.md` 的「创始人只说人话」表 + frontmatter 触发词 | **加载 Skill 的 Agent**（必然读到） | **能力本体**：映射表只在这里 |
| 细则层 | `assets/人话入口.md` | Agent 按需读 | 完整映射、三条硬边界、`go` / `advance` / `pm` 之分、歧义消解 |
| 入口层 | `entry_block()` 写进宿主入口文件的受控区块（`opc init` / `opc attach --apply`） | 会话启动时自动进上下文的 Agent | **指针 + 约束 + 事实**：告诉 Agent「路由表在 Skill 里，先加载 Skill」；**不放能力副本** |

三层都来自**同一个包**，所以任何用户 `init` 完就具备同样能力：宿主入口文件是**指针层**，不是**能力层**。

### 44.2 入口文件里长什么样

`opc init`（无宿主入口时新建 `AGENTS.md`）与 `opc attach --apply`（已有项目合并受控区块）写入的受控区块包含：

- 原有 7 条纪律（先读规范、读岗位卡、按需加载、闸门只出草稿、只读规则层、上下文有限用 `opc bots` 投影、简历只读自己那份）；
- **本机事实**：Vault 绝对路径、脚本绝对路径、解释器路径、相对工作区根路径 —— 免得每个会话重复探测；
- **指针**：路由表在 Skill 里（规则层 `SKILL.md` / 细则层 `assets/人话入口.md`）→ Agent **先加载 Skill** 再翻译创始人的人话；
- **三条硬边界**：闸门拍板权归创始人 / 一会话一 role / 禁止互相唤醒（**约束**，不是能力，留着能防止 Agent 没加载 Skill 时擅自拍板）。

> 区块里**刻意没有**「人话 → 命令」映射表 —— 理由见 §44.6。

区块由 `opc attach` 维护，**幂等**（重复执行只更新内容，不叠加）；`opc attach --remove` 移除；区块外的内容一行不动。

### 44.3 命令速查（话术 → 命令）

> 本表住在**包里**（属能力层）。宿主入口文件里**没有**这张表 —— Agent 要用就得加载 Skill。

完整表见 `assets/人话入口.md` §2，摘要：

| 创始人说 | Agent 跑 |
|---|---|
| 「继续推进」「继续」 | `handoff` → 非闸门 `advance`；闸门停下问创始人 → 拿到结论才 `go --decision` |
| 「<项目名> 继续推」 | `handoff --project <项目名>` → 同上 |
| 「该派活给谁」 | `pm`（只读面板）+ `triage`（定范围，落派活清单） |
| 「以 <role> 身份接棒」 | `role` → `scaffold --role` → 干活 → `done --role` |
| 「可以沉淀知识了」 | `distill` → `link`（口语触发即执行） |

### 44.4 三条硬边界（Agent 不得自行突破）

1. **闸门拍板权永远在创始人**（阶段 0 / 2 / 7）：`advance` 在闸门阶段拒绝；**「继续」不算闸门结论**。
2. **一次会话只绑定一个 role**：换角色必须开新会话；新会话第一句说「继续」即可接上。
3. **Agent 之间禁止互相唤醒**：下一棒等创始人确认。

### 44.5 边界说明

- v2.19 只改**交互层**，不改流程语义：九步链、闸门位置、owner 归属、落点规则全部不变 → **规范版本仍 v2.18**。
- v2.20 只改**入口层形态**（能力副本 → 指针），仍不动流程语义 → **规范版本仍 v2.18**，本包版本升 v2.20.0。
- 宿主中立：本节不出现任何宿主专名；宿主入口文件名清单（`AGENTS.md` / `CLAUDE.md` / …）属**多宿主并列适配**，可用 `attach --entry` 指定。

### 44.6 为什么入口层不放映射表（测试保真度）

宿主入口文件（`AGENTS.md` 等）是**会话启动就自动进上下文**的宿主环境。把映射表抄一份进去看着"更稳"，实际有三个问题：

1. **测试失真（最要命）**：抄本让 Agent 不加载 Skill 也能照表把活干完 → 「全新安装测试」永远是**假阳性**，测不出 Skill 真本事。抄本是**替 Skill 干活**，不是帮 Skill。
2. **口径漂移**：抄本与包是两份文本，改一处忘另一处，两边说法打架且无人察觉。
3. **绕过约束**：抄表只给命令，不带规范、岗位卡、落点规则 —— Agent 照抄本走，反而可能不读 `OPC-架构规范.md` 就动手。

指针式反而更稳：Agent 顺着指针去加载 Skill → 走**唯一真相源**，顺带带上规范、岗位卡、落点规则；三条硬边界仍留在入口层，因为它约束的是**行为**而不是**能力**。

> 回归护栏：`scripts/selftest_nlu.py` §5 会断言入口层**不含**任何触发语与命令名（`handoff` / `advance` / `scaffold` / `distill` / `triage` / `go --decision`）与映射表管道行。**谁想把抄本加回去，自测会红。**

## v2.28 群内门铃与岗位主动交互（2026-11-20 实测修）

**交互模型**：叫醒下一棒 → 下一棒自己领活 → 岗位要交互时主动 @ 创始人。

| 环节 | 谁 @ 谁 | 命令 / 机制 |
|---|---|---|
| 叫醒下一棒 | pm @ 下一棒 bot | `opc new` / `opc go` / `opc advance` 自动发**门铃**（`wake_next_role()`） |
| 领活 | 下一棒自己 | `opc claim --role <role> --project <PXXX>`（pull 式） |
| 要交互 | **岗位 @ 创始人** | `opc ask --role <role> --project <PXXX> --text "..."` |
| 创始人回话 | 创始人 @ 该岗位 | `require_mention=true` → 只有被 @ 的岗位醒 |

**修掉的 4 个真实缺陷**：

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| W1 | `opc new` 建项后不发任何通知 | 第一棒永远没人叫醒 → 链卡在阶段 0 | `cmd_new` 末尾调 `wake_next_role()` |
| W2 | 推进只通知创始人，从不叫醒下一棒 | 通知发出去了，下一棒仍在睡觉 → 链断在半路 | `cmd_go` / `cmd_advance` 均调 `wake_next_role()` |
| W3 | 岗位卡写「用自己身份 @ 创始人」，但**没有任何命令能执行** | 岗位到交互点只能把问题烂在本地文件 → **创始人在群里零感知** | 新增 `opc ask` |
| W4 | `profile_root` 未 `expanduser()` | 配置写 `~/.hermes/profiles`，而 `Path("~/...")` 是字面量相对路径 → 所有「按 profile 找凭证」全读空 | `dispatch._profile_env()` 展开波浪号 |

**飞书 @ 的三个坑（实测，别的用户必踩）**：
1. @ 一个 bot 必须在 `at` 节点填**该 bot 自己视角的 open_id**（用**它自己的** app 凭证调 `/bot/v3/info` 取得）。
   填 `app_id`（`cli_xxx`）→ 飞书解析成**空 user_id**（`"user_id":""`）→ 门铃**静默失效**。
2. **发送方与被 @ 方不能是同一个 bot**：用目标自己的身份给它发指令 → 飞书判为「自己发的」，
   接收侧**根本收不到**（日志里连 inbound 记录都没有）。指令必须由第三方（pm）身份发，
   或让目标自己执行命令（`opc ask`）。`send_group_at_open_id()` 已加同位守卫。
3. 读群消息要 `im:message.group_msg` 权限，缺权限时**无法从服务端独立验证送达**——
   只能以发送回执（code=0 + message_id）为凭据，别谎称「已读」。

**自测**：`scripts/selftest_wake.py`（15 项，覆盖 W1–W4 + 自发自收守卫）。
