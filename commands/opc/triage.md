pm 起草**派活清单**——本次项目路由的唯一真相源。

**脚本**：`<skill包目录>/scripts/opc.py triage`（`<skill包目录>` = 本 Skill 包所在目录，与宿主无关）。定位顺序：① 环境变量 `OPC_SKILL_DIR`；② 宿主注入的 skill 目录变量（指向包目录本身或其父目录）；③ 目录结构约定：`<本命令文件所在目录>/../../skills/opc-team/`（多数宿主把 `commands/` 与 `skills/` 放在同一配置根下）；④ 在工作区与用户主目录搜 `opc-team/scripts/opc.py`。用宿主可用的 Python 解释器以绝对路径调用。

**落点**（结构化，永远在 Vault 内，不散落在临时目录）：

| 形态 | 路径 |
|---|---|
| 机器可读（唯一真相源） | `<项目目录>/_派活清单.json`（项目未建项时落 `99_Agent配置/_派活清单/<项目号>.json`） |
| 人可读 | `<项目目录>/_派活清单.md` |
| 回写小节 | `<项目目录>/4_产品基线.md` 的 `## 本次涉及岗位与产出资产清单`（该文件存在时才写） |

**步骤**

1. 逐岗位执行 `triage`（可多次调用，同岗位后写覆盖先写）：
   - 派活：`--role <岗位> --assets <产出资产> --reason "<分诊理由>"`
   - 不涉及：`--role <岗位> --involved no --reason "<理由>"`
   - 零岗位：`--zero --reason "<理由>"`
   - 查看：`--show`
2. `--reason` **必填**，漏写直接报错；岗位名必须在 `role_bindings` 登记。
3. 建项：`opc new "<项目名>" --triage <清单文件>`（清单自动搬进项目目录）。
4. 汇报派了谁、没派谁、各自理由，并给出下一步命令。

**硬约束**

- **解析失败一律显式报错并中止建项**——找不到清单小节 / 没有一行判出「涉及」/ 判定词不认识 / 岗位名未登记 / JSON 坏，**都不会**偷偷按全量 9 步派活。
- **不带 `--triage`** 仍按全量 9 步，但必须明确告知用户这一点。
- 清单里的「零岗位」是合法写法，不算错。

**完成标准**：清单已落盘且内容与分诊判断一致；下一步命令可直接执行。

**深入**：派活口径 → 规范 §15.14；落点与报错口径 → 手册 §38。
