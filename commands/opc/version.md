管理 OPC 项目的**版本链**。

**脚本**：`<skill包目录>/scripts/opc.py version <子命令>`（`<skill包目录>` = 本 Skill 包所在目录，与宿主无关）。定位顺序：① 环境变量 `OPC_SKILL_DIR`；② 宿主注入的 skill 目录变量（指向包目录本身或其父目录）；③ 目录结构约定：`<本命令文件所在目录>/../../skills/opc-team/`（多数宿主把 `commands/` 与 `skills/` 放在同一配置根下）；④ 在工作区与用户主目录搜 `opc-team/scripts/opc.py`。用宿主可用的 Python 解释器以绝对路径调用。

**何时用**

- 用户说「这个项目要加个新需求」「再改一版」「这次的需求跟上次不一样」→ **追加立项**（`version new`）。
- 用户问「这个项目改到第几版了」「之前有几版」→ **查看台账**（`version list`）。

**步骤**

1. **确定项目**：用户没点名就问，或用 `opc.config.json` 里的当前项目（`--project` 接受**项目名 / 项目号 / 目录名**任意一种）。
2. **`version list --project <项目>`**（只读）：一个版本一行 —— 版本号 / 立项时间 / 本次需求 / 状态 / 产出份数 / 沉淀状态 / 沉淀时间。汇报给用户。
3. **`version new --project <项目> --需求 "<这次要做什么>" --founder-approved "<同意依据>"`**：
   - **立项是创始人决策点（v2.29.5）**：先问创始人「这个需求要不要立项」，拿到**明确同意**才执行；未带 `--founder-approved "<同意依据>"` 一律拒绝、**不占号**（不代拍板、不默认放行，任何岗位都一样）；同意依据留痕进版本台账。
   - `--需求` **必填**，缺了直接报错（不静默占号）—— 先把这次要做什么问清楚。
   - 派活：缺省沿用项目里上一版的 pm 派活清单；用户给了新的派活范围就加 `--triage <清单文件>`。
   - 脚本会：拿到下一个版本号（**只增不复用**）→ **只登记不产文件**（建 `V<N>/` 版本目录，等岗位开工）→ 追加索引行与版本台账行 → 重建交接链（起点 = 新版本第一个被派的岗位）。
4. 汇报：新版本号、这次带了哪些岗、交接链下一棒（**产出文件此时还不存在**，岗位开工时各自 `opc scaffold`）。

**要点（v2.17 · 规范 §15.18；v2.18 · 规范 §15.19）**

- **版本 = 一次立项**：创建项目 = V1；项目内确认「这个需求要做」= V2、V3…。
- **立项是创始人决策点（v2.29.5）**：立项不占闸门游标，但**新版本号 = 新立项，必须经创始人同意**（`--founder-approved` 留痕）。闸门管的是「这一步能不能过」，不是「能不能开始做」。
- **一个版本 ≠ 走完九步**：一个版本只带这次真要干的活，派谁由 pm 派活清单决定；没有清单才回退全量 9 步。
- **v2.18：产出按「版本目录 → 职业目录」落盘**（`2026-12-03-V2/design/5_设计交付.md`），**立项只登记不生成任何文件**；岗位开工时 `opc scaffold --role <role>` 只生成自己那一份。
- **人读处不带 `P00X`**：目录名 `项目名`（同名加 `-2`，不带日期），版本目录 `YYYY-MM-DD-V<N>`（日期 = 该版本立项日），短 ID 只在索引末列 `ID` 与状态文件名里。

**完成标准**：版本台账多了一行（或已列出），产出索引出现该版本行，交接链指向新版本起点。

**深入**：手册 §42 / §43；规范 §15.18 / §15.19。
